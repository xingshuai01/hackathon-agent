## 1. 决策一：`ToolContext` 加不加 `emit` —— 已消解，不需拍板

### 原来为什么觉得要拍板

`knowledge_hit` 事件定义了、CLI 渲染器也实现了（`renderCli.ts:75`），但**从来没有代码发出它**。
我当时的判断是：只有工具自己知道命中了哪一页，而工具拿到的上下文是 `ToolContext`，
它里面没有 `emit` —— 所以要发这个事件，只能改冻结契约。

### 核实后：这个判断是错的

`knowledge_search` 不是裸工具，而是**工厂**：

```ts
// src/main.ts:211
createKnowledgeSearchTool({ store, events: bus, ... })
```

只要给工厂的 options 加一个字段，工具内部就有地方发事件了。契约完全不用动：

```ts
// src/services/knowledge/tool.ts
export interface KnowledgeHitSink {
  emit(event: {
    readonly type: 'knowledge_hit'
    readonly noteId: string
    readonly paperId: string
    readonly page: number
    readonly description: string
  }): void
}

export interface KnowledgeSearchOptions {
  readonly store: KnowledgeStore
  readonly events?: KnowledgeHitSink   // ← 新增,可选
  // …
}
```

`EventBus` 结构上就是这个窄接口的超集，所以 `main.ts` 直接传 `bus` 能通过类型检查
（`npm run typecheck` 已验证），而 A 不需要 import `ui/events.ts`，
不会因为 UI 层改事件定义而被拖着改。

### 已经做完了

| 动作 | 位置 |
|---|---|
| 新增 `KnowledgeHitSink` + `events?` 选项 | `src/services/knowledge/tool.ts` |
| 命中后逐条 `emit`（零命中不发；上报口抛错只降级，不让工具失败） | 同上 |
| `main.ts` 传 `events: bus` | `src/main.ts:211` |
| 4 个用例（带锚点、零命中不发、上报抛错不失败、不传时静默） | `test/knowledge/tool.test.ts` |

门禁：**315 pass**（311 → +4）。

### 结论

**给 Web 负责人的一句话**：跑一次 `ask` 且命中知识库时，`knowledge_hit` 会真的出现在事件流里了，
字段是 `{ noteId, paperId, page, description }`，可以直接拿去高亮。
你不必为此改任何代码，只要订阅总线。

**剩余的 `tool_generated` 不属本条**。它在 B 的 ingest 流程里发，`main.ts` 已经有 emit 通道，
不用改契约 —— 见 §5。

## 2. 决策二：生成物提交策略

### 现状

| 路径 | 现在 | 谁生成的 |
|---|---|---|
| `knowledge/README.md` | 已入库 | 手写 |
| `knowledge/<paperId>/notes.md`（约 15KB/篇） | **未被忽略**，一旦 ingest 后提交就会进库 | A 的 `ingest` |
| `skills/README.md`、`skills/ai-code-review-gate/SKILL.md` | 已入库 | 手写 |
| `skills/_drafts/<skillId>.md`（几 KB） | 目录还不存在；生成后**不会被忽略** | C 的草案生成 |

### 建议（三档分开处理）

| 对象 | 建议 | 理由 |
|---|---|---|
| `knowledge/<paperId>/notes.md` | **不提交**，加忽略 | 纯派生物，一条命令可重建；且 `createdAt` 是运行时刻，两人各跑一次就产生大量无意义 diff。体积也不小（20 条 ≈ 15KB，10 篇论文就 150KB） |
| 一份**固定样例** | 提交到 `fixtures/knowledge/` | 演示与评审需要“打开就能看”，又不污染生成目录。取 ReAct 那篇的产物，一次性冻结 |
| `skills/_drafts/*.md` | **提交** | 几 KB；它是**人工审核待办清单**（数据铁律 #4：技能未经人工审核不得 `active`）。提交它，评审能看到“论文 → 技能草案 → 待补哪几节”的完整证据链 |
| 已晋升的 `skills/<id>/SKILL.md` | **提交** | 是资产不是产物，且已有示例技能在库里 |

具体改动只有一行（`.gitignore`）：

```gitignore
# 知识页是派生数据,可重建;固定样例见 fixtures/knowledge/
/knowledge/*/
!/knowledge/README.md
```

### 谁来决定

**不属于任何单个模块**：它影响 `git status` 的干净程度和最终提交材料的观感，
应该由**提交负责人（或组长）**一次定掉，A/B/C 三人照做即可。
B 完全不受影响 —— `src/tools/generated/` 是源码目录，本来就要提交。

> 如果你的判断是“评审就想看到仓库里真有一批知识页”，那就反过来：提交 `knowledge/`，
> 但**在 ingest 时把 `createdAt` 固定为论文年份**这种可复现取值。
> 两条路都行，**唯一不能接受的是不定**——不定的话，谁先提交谁定。

## 3. 决策三：`AtomicNote.section?` —— 我建议撤回

### 我之前怎么说的

> “`section` 是 C 模块证据索引要用的信息，抽取侧已经拿到却只能丢弃。”

**这句话是我说过头了。** 核实结果：

```ts
// src/services/skills/types.ts:81
readonly evidenceIndex: readonly { readonly claim: string; readonly noteId: string }[]
```

C 的证据索引只要 `claim + noteId`，**不看章节**。
而在 `docs/SRS.md` / `docs/SDD.md` 里全文搜 `section`，只命中技能自身的 `sections`（七节），
没有任何一条需求要求知识页记住自己出自哪一章。

### 所以

| 事项 | 结论 |
|---|---|
| 加 `section?: string` 到冻结契约 | ❌ **不加** |
| `docs/wyh/PR-知识页section字段.md` | 已标注「暂不实施」，不要提交 PR |
| 它唯一的真实价值 | 人读 `notes.md` 时知道这页来自哪一章 —— 属于展示层优化 |
| 什么时候再提 | Web 的「知识库」面板真要做“按章节分组浏览”时。那时连 `kind` 都可能要一起重估 |

**代价接近于零**：A 的验收（AC-A1.1~A5.2）没有一条要求章节；
`extract.ts` 内部仍然按章节算权重挑样，只是不把这个字段落进契约。
真要展示，用 `## p{page} · {hash6}` 这种段标题带一行章节名即可，连契约都不用碰。

一句话：**别为了一个没有需求出处的字段去动冻结契约**，那是拿全组的合并冲突换一个没人用的字段。

## 5. 顺带：B 唯一需要知道的一件事（不是拍板）

`tool_generated` 事件由 **B 的 ingest 流程**发出，不要指望 A 或骨架替你发：

```ts
import { bus } from '../ui/events.ts'   // services 目录可以 import ui,已核对边界规则

bus.emit({
  type: 'tool_generated',
  toolName: spec.name,
  sourcePaper: doc.paperId,
  status: 'draft',        // 人工审核通过前只能是 draft,对应数据铁律 #4
})
```

三条硬约束（都已写进 `B开工前审计.md` §3，这里再压缩一遍）：

1. **只改 `src/tools/generated/registry.generated.ts`**，不要动 `main.ts` —— 避免两人同时改同一个文件。
2. `src/tools/**` 的 import 白名单只有 `src/tools/`、`src/ui/`、`src/agent/types`、`node:`、`zod`。
   **不能** import `toolsynth` 的业务类型，只能在本地声明最小结构。

## 0. 核心结论

1. **A、B、C 不是三个项目，而是一条链的三层**：同一批论文 PDF → 抽取为「原子知识页」（A）→ 把其中的方法固化为「可执行工具」（B）→ 把跨论文的领域共识固化为「专家技能」（C）。三者共享同一个抽取底座和同一套溯源坐标（`paperId + 页码 + 章节`）。
   → **如果分成三个独立项目做，PDF 解析要写三遍，切片 schema 会不一致，最终三者无法互相引用。这是本方案最大的架构风险，必须在第一天用一份 schema 冻死。**
2. **「切片」这个词在 KiwiFS 语境下需要重新定义**。KiwiFS 的检索单位是**页面（Markdown 文件）**，不是向量库里的 chunk。按 512 token 机械切片会让一篇论文炸出 200+ 个碎片页、单页失去主语、引用断链。正确做法是**双层切片**：原文层（一篇一页）+ 原子知识层（一个论断一页），向量切片从原子页派生并携带页码锚点。详见 §4.2。
3. **B 是三者中唯一有真实失败风险的**。A 和 C 的产物是文本，质量好坏可读可判；B 的产物要能跑，而「论文里的方法描述」到「可执行的参数化工具」之间存在语义鸿沟。必须分级：L1（方法选型 + 参数填充）做，L2（多步流程 DSL）带人工确认做，L3（自动生成分析代码）不做。
4. **4 天做不完三项完整版**。按 §8 的「纵向薄切片」策略：D1 打通底座与 A 的最小闭环，D2 长出 3 个工具，D3 长出一个 skill 并串成一条命令，D4 打磨。演示叙事是「新论文进来自动长知识、长工具、长技能」，而不是展示三个独立模块。
5. **每个需求都必须有可量化的验收**（§13）。文本类产出最容易陷入「看起来还不错」，必须用 locator 可验证率、检索命中率、复现一致性、领域测试题准确率这些硬指标卡住。

## 2. 三者关系：一条流水线，三层沉淀

```
                    ┌─────────────────────────────────────┐
                    │  论文 PDF（一批同领域文献）           │
                    └────────────────┬────────────────────┘
                                     ↓  【共享底座】解析 + 结构化抽取（一次实现，三处复用）
                    ┌─────────────────────────────────────┐
                    │  论文结构化产物                       │
                    │  paperId / 章节树 / 页码锚点 / 元数据  │
                    └───────┬──────────────────┬──────────┘
                            ↓                  ↓
              ┌──────────────────┐   ┌──────────────────────┐
              │  A · 知识层       │   │  B/C 的方法来源        │
              │  原子知识页        │   │  方法描述 + 参数 + 前提 │
              │  「事实」          │   │  「动作」              │
              └────────┬─────────┘   └──────────┬───────────┘
                       │                        ↓
                       │             ┌──────────────────────┐
                       │             │  B · 工具层           │
                       │             │  参数化工具 + MCP      │
                       │             │  「能做什么」          │
                       │             └──────────┬───────────┘
                       ↓                        ↓
              ┌─────────────────────────────────────────────┐
              │  C · 技能层                                  │
              │  领域框架 + 流程判据 + 工具映射 + 失败模式      │
              │  「怎么判断、先做什么」                        │
              └─────────────────────────────────────────────┘
```

三层的沉淀物性质完全不同，这是它们必须分开存的原因：

| 层 | 沉淀什么 | 载体 | 使用者 | 更新频率 |
|---|---|---|---|---|
| **A 知识层** | 事实与论断（可引用） | KiwiFS 知识页（Markdown + frontmatter） | 人 + agent 检索 | 每读一篇论文 |
| **B 工具层** | 可执行动作（有契约） | TS 工具 + MCP server | agent 调用 | 每提炼一个方法 |
| **C 技能层** | 判断力（何时用哪个） | Skill 文件（Markdown + frontmatter） | agent 按需加载 | 每形成一个领域共识 |

一句话概括三者边界：**A 记"是什么"，B 做"怎么做"，C 判断"该做什么"。**

反过来也成立：如果某个信息在 A 里只是描述、在 B 里有确切实现、在 C 里是选择依据——它就该在三处各有一份，并通过 `paperId + locator` 互相锚定，而不是复制三遍正文。

## 3. 共享底座（先做这个，否则三项都要返工）

无论 A/B/C，第一道工序完全相同，必须一次实现：

```ts
// services/pdf/ —— 输入 PDF，输出结构化论文产物
export type PaperDoc = {
  paperId: string            // 稳定 ID：优先 DOI / arXiv ID，否则 sha256(file)[:16]
  title: string
  authors: string[]
  year: number
  venue?: string
  sections: Array<{
    heading: string
    level: number
    paragraphs: Array<{ text: string; page: number }>   // ★ 页码锚点，全局最重要
    tables: Array<{ caption: string; markdown: string; page: number }>
    figures: Array<{ caption: string; page: number; bbox?: [number, number, number, number] }>
  }>
  abstract: string
  references: Array<{ raw: string; doi?: string; arxivId?: string }>
  parseQuality: { pagesParsed: number; pagesTotal: number; hasOcr: boolean }
}
```

四条硬性要求：

| 要求 | 理由 | 违背后果 |
|---|---|---|
| **每个段落必须带 `page`** | 所有引用、所有证据、所有复现都要能回指到「第几页第几节」 | 无法验证抽取是否幻觉，A/B/C 全部失去可信度 |
| **`paperId` 必须稳定可推导** | 重复入库、增量更新、跨库引用都依赖它 | 同一篇论文进库两次，知识图谱出现重复节点 |
| **`parseQuality` 必须显式** | 解析失败的论文要能被过滤，而不是产出垃圾知识 | 幻觉溯源到一篇根本没解析好的 PDF，最难查 |
| **表格必须转 Markdown** | 论文的核心结果 80% 在表里，纯文本流会丢失行列对应 | A 抽不出定量结论，B 抽不出参数取值 |

**技术选型建议**：`pdfjs-dist`（纯 JS，跨平台，可拿 bbox）或 `unpdf`；学术 PDF 优先走 **arXiv 官方 HTML/元数据 API**（质量远高于 PDF 解析），PDF 解析只作降级路径。

> 注意 `parseQuality.pagesParsed / pagesTotal` 这一对指标：如果低于 0.7，这篇论文应直接标记 `quarantined`，不进入 A 的抽取队列。**宁可少 20 篇，不要脏 1 篇**——脏数据会污染 C 的领域共识，而 C 是可复用的长期资产。

## 4. 需求 A · 知识库

### 4.1 可行性结论

| 维度 | 评级 | 说明 |
|---|---|---|
| 技术可行性 | **高** | KiwiFS 已提供多库、检索、图谱、MCP，本需求主要是「抽取 + 组织」，不是「造平台」 |
| 工作量（MVP） | 2–3 天 | 单库、20 篇、原子页、图谱可视 |
| 主要风险 | 中 | 抽取质量与幻觉；「切片」定义错误；自建前端容易失控 |
| 建议 | **做，且作为整条链路的第一站** | A 的 locator 体系是 B/C 的地基 |

### 4.2 关键判断：「切片」应该切成什么

这是本需求最重要的一条工程决策，值得单独说明。

**错误做法（多数 RAG 教程的默认路径）**：把论文全文按 512 token 切块，每块写成一个小 md 文件塞进知识库。

后果是可以预见的：

| 后果 | 具体表现 |
|---|---|
| 页面爆炸 | 30 页论文 → 150–250 个碎片页。知识图谱变成毛线球，人不可读 |
| 单页失去主语 | 「该方法提升了 3.2%」——哪个方法？碎片化后指代消失 |
| 引用断链 | 检索命中一个块，无法回溯它在论文哪个论证环节 |
| 与 KiwiFS 模型冲突 | KiwiFS 是「一页一概念」的 wiki 模型，不是 chunk 仓库。用 wiki 表达 chunk，等于用两种模型互相磨损 |

**推荐做法：双层切片**

```
L0 原文层（一篇论文 = 一页）
  pages/sources/<paperId>.md
  ├── frontmatter: paperId / title / authors / year / doi / arxivId / parseQuality
  └── 正文：保留原章节结构，每个段落末尾带 {p.7} 页码标记

L1 原子知识层（一个论断 = 一页）★ 这才是"知识提取"的产物
  pages/notes/<paperId>-<slug>.md
  ├── frontmatter:
  │     claimType: method | finding | dataset | limitation | definition
  │     source: "[[sources/<paperId>]]"
  │     locator: "p.7 §4.2"              ← 必须可验证
  │     confidence: high | medium | low
  │     tags: [领域标签]
  └── 正文：一句话断言 + 支撑证据（1-3 句原文摘录）+ 我的复述

L2 向量切片（可选，仅在启用向量检索时）
  由 L1 页面派生，每片携带 pageId + sourceLocator
  检索命中 → 直接返回 L1 页 → 回指 L0 的页码
```

**为什么这样切**：

- 与 KiwiFS 的检索模型对齐（页级 FTS5 + 页级向量），召回结果是**有意义的页面**而不是碎片；
- 一页一论断，天然满足「引用可回溯」——页面上直接写着 `locator: p.7 §4.2`；
- 图谱（backlinks / graph view）才有信息量：节点是概念和论断，边是「支持 / 反驳 / 引用 / 使用同一方法」；
- 成本可控：20 篇论文约产出 200–400 个原子页，人还能审得过来。

**切片数量参考**：一篇 20 页实证论文 → 6–12 个原子页。若超过 20 个，说明粒度太细（在切句子）；若少于 3 个，说明抽取太粗（在写摘要）。

### 4.3 KiwiFS 能力 → 需求映射

| 需求要素 | KiwiFS 提供的能力 | 用法 |
|---|---|---|
| **多个库** | `multi-space`：一个 server 多个隔离工作区，各自独立 git repo 与搜索索引 | 按「研究项目 / 研究问题」切库，不按学科切。理由见下 |
| **可视化界面** | 内置 Web UI：块编辑器、`[[wiki links]]`、backlinks、知识图谱（Sigma.js）、Cmd+K 搜索、暗色 | **直接用，不自建**。这是本需求最大的省时点 |
| **结构化查询** | frontmatter 映射到 SQLite `file_meta`，支持 DQL（类 SQL：`TABLE / WHERE / SORT / GROUP BY`） | 生成「证据矩阵」：按 `claimType + year + method` 聚合导出 CSV |
| **全文检索** | SQLite FTS5 + BM25 ranked | 关键词召回，中文需确认分词支持（见风险 R4） |
| **向量检索** | 可插拔：OpenAI / Ollama / ONNX + sqlite-vec / Qdrant | 语义召回；不启用也有 FTS5 兜底 |
| **溯源** | 每次写入是原子 git commit；`X-Actor` / `X-Provenance` 头记录来源 | 「这一页是谁写的、从哪来」有据可查，B/C 复用 |
| **知识维护** | content health：stale 页检测、断链、孤儿页、矛盾检测 | 定期跑，清理 `orphan` 与重复论断 |
| **Agent 接入** | MCP server（`kiwi_read` / `kiwi_write` / `kiwi_search` / `kiwi_tree` / `kiwi_query_meta` / `kiwi_bulk_write`）+ REST | 主路径走 **MCP**；批量导入走 REST（见下） |

**库怎么切**：建议「一个研究项目一个 space」。不要按学科切（`经济学/`、`生物学/`）——学科边界模糊且会无限膨胀；按项目切可以随项目结束归档，git 历史也更有意义。跨库检索用一个 `_index` 汇总 space 或 DQL 联合查询解决。

**写入路径**：批量入库（一次几百页）走 REST `bulk_write`，单页修订走 MCP。不要用 MCP 逐页写——每页一次 round-trip，几百页会拖到分钟级。

### 4.4 抽取流水线

```
PaperDoc ──► [1] 章节切分 + 段落编号
          ──► [2] 论断抽取（LLM + 严格 schema，citation-first）
          ──► [3] locator 校验（★ 关键，见下）
          ──► [4] 去重合并（同 paperId 内 + 跨 paper 的相似论断）
          ──► [5] 渲染为 Markdown + frontmatter
          ──► [6] 批量写入 KiwiFS（REST bulk_write）
          ──► [7] 触发索引重建 + 生成 backlinks
```

**[3] locator 校验是整条流水线的质量闸门**，必须实现，不能省：

```ts
// 校验逻辑：抽取出的"证据原文"必须能在 PaperDoc 对应页码的文本中命中
function verifyLocator(claim: ExtractedClaim, doc: PaperDoc): VerificationResult {
  const pageText = doc.sections
    .flatMap(s => s.paragraphs)
    .filter(p => p.page === claim.page)
    .map(p => p.text).join(' ')
  // 归一化：去空白、统一引号、去连字符断行
  const norm = (s: string) => s.replace(/\s+/g, '').replace(/[""'']/g, '"').toLowerCase()
  const hit = norm(pageText).includes(norm(claim.quote).slice(0, 120))
  return hit
    ? { ok: true }
    : { ok: false, reason: 'QUOTE_NOT_FOUND_ON_PAGE', claimId: claim.id }
}
```

不通过校验的论断有两种处置：**重试一次抽取**（把原文页码段落贴给它，让它重写）；**仍失败则丢弃并计入 `hallucinationRate`**。

这个比率是本项目最有说服力的指标之一：`hallucinationRate = 丢弃数 / 抽取总数`。能报出一个「我们的抽取有 3.7% 的论断因无法在原文定位而被自动丢弃」的数字，比任何"效果很好"的描述都可信。

### 4.5 可视化：要用到什么程度

| 层次 | 做法 | 成本 | 建议 |
|---|---|---|---|
| L0 | KiwiFS 内置 Web UI（浏览、搜索、图谱、backlinks） | 0 | **必做，即默认交付** |
| L1 | 用 DQL 导出的证据矩阵 → 静态 HTML（表格 + 筛选） | 0.5 天 | 演示价值高，建议做 |
| L2 | 自建前端（React + REST） | 2–3 天 | **不做**。这是本需求最大的范围陷阱 |
| L3 | 知识图谱定制布局、时间线、引文网络 | 3 天+ | 不做 |

判断标准很简单：**内置 UI 能表达的信息，一律不自建**。真正需要定制的只有一类视图——「跨论文的证据对照表」，而它用 DQL 导 CSV 就能解决 90%。

### 4.6 风险与缓解

| 编号 | 风险 | 触发信号 | 缓解 |
|---|---|---|---|
| R1 | 抽取幻觉 | `hallucinationRate` > 10% | locator 强制校验 + 丢弃而非修补；prompt 里禁止"总结性发挥"，只允许"摘录 + 复述" |
| R2 | PDF 解析质量差 | `parseQuality < 0.7` 占比 > 20% | 优先 arXiv HTML/元数据；扫描件走 OCR；仍差则隔离 |
| R3 | 原子页粒度失控 | 单篇产出 > 20 页 或 < 3 页 | 在 prompt 里给正反例（few-shot 3 个），并统计每篇页数分布做校准 |
| R4 | 中文检索效果差 | 中文关键词搜不到已有页面 | SQLite FTS5 默认分词对中文不友好，需验证；不达标则启用向量检索（ONNX 本地模型）或建 `tags` 同义词表走 `file_meta` 精确过滤 |
| R5 | 重复入库 | 同一论文出现两个 pageId | `paperId` 必须由 DOI/arXivId 推导，入库前查 `file_meta` 去重 |
| R6 | 成本失控 | 单篇 token 消耗异常 | 抽取输入只给「当前章节」而非全文；缓存 PaperDoc；批量夜间跑 |

### 4.7 MVP 定义与验收

**MVP 范围**：1 个 space、20 篇同领域论文、原子页 200+、内置 UI 可浏览可搜索、证据表可导出。

| 验收项 | 命令 / 动作 | 通过标准 |
|---|---|---|
| 批量入库 | `npm run ingest -- --space econf --papers ./data/pdfs` | 20 篇全部入库，无重复 `paperId` |
| 原子页产出 | 查 KiwiFS `kiwi_tree` 或 REST | `pages/notes/` 下 ≥ 200 页，每页有 `source` + `locator` |
| 溯源可验证 | `npm run verify:locators` | 抽样 50 页，locator 命中率 ≥ 95% |
| 检索可用 | UI 搜 10 个预设问题 | Top-5 命中率 ≥ 80% |
| 图谱可用 | 打开 UI 图谱视图 | 节点 ≥ 200，无孤立簇（孤儿页 < 10%） |

## 5. 需求 B · 工具库

### 5.1 可行性结论

| 维度 | 评级 | 说明 |
|---|---|---|
| 技术可行性 | **中** | 不是工程难度，是**语义鸿沟**：论文的方法叙述 ≠ 可执行契约 |
| 工作量（MVP） | 2 天 | 15 个分析基元 + 8 个参数化工具 + MCP server + run manifest |

### 5.2 分级：什么能自动化，什么不能

| 级别 | 形态 | 自动化程度 | 可行性 | 决策 |
|---|---|---|---|---|
| **L1 参数化工具** | 「选基元 + 填参数」：论文写 *"two-sided Welch's t-test, α=0.05"* → `stat_test(kind="welch_t", alpha=0.05, alternative="two-sided")` | 全自动 | **高** | **做**。前提是预置基元库 |
| **L2 流程 DSL** | 多步流程抽取为步骤序列：`dropna → standardize → PCA(n=10) → KMeans(k=5) → silhouette` | 半自动（人工确认） | **中** | **做，但必须人工 review 后固化** |
| **L3 生成分析代码** | 直接生成 pandas/sklearn 脚本并期望跑对 | 全自动 | **低** | **不做主线**；只做「生成草稿 + 人改写」 |

**为什么 L3 不行**：生成代码要同时猜对四件事——数据 schema、库版本、统计前提、边界条件。任一猜错就是"跑通了但结果是错的"，这比跑不通危险得多。复现场景下，**静默的错误结果比明确的失败更有害**。

**为什么 L1 可行**：它把开放问题收窄成封闭问题。基元库（15–25 个函数）是有限的，抽取任务是「分类 + 参数填充」，这是 LLM 最擅长的两类任务。语义鸿沟被基元库的边界吃掉了。

### 5.3 核心设计：方法工具三件套

一个「工具」不是一段代码，而是**契约 + 实现 + 证据**三件套。缺任何一件，都不算可复现。

```ts
// 1) 契约：机器可校验
export type MethodTool = {
  toolId: string                    // 稳定 ID：<domain>.<method>.<variant>，如 stats.hypothesis.welch_t
  version: string                   // semver，实现变更必须升版
  inputSchema: JSONSchema           // 参数
  outputSchema: JSONSchema
  preconditions: Precondition[]     // ★ 前提假设，最容易漏
  failureModes: string[]            // 已知的失败方式，直接进 prompt 帮模型避坑
  evidence: {
    paperId: string
    locator: string                 // "p.7 §4.2"
    quote: string                   // 论文原文引句
    extractedBy: { model: string; at: string }
  }
}

type Precondition = {
  id: string                        // 'normality' | 'equal_variance' | 'no_missing'
  description: string               // 给人和模型读
  check: 'auto' | 'manual' | 'none'
  checkImpl?: string                // 可自动检查的，指向一个 dataCheck 基元
}
```

```ts
// 2) 实现：模板化，不自由生成
export const welchT = defineMethodTool({
  toolId: 'stats.hypothesis.welch_t',
  version: '1.0.0',
  params: z.strictObject({
    alpha: z.number().min(0).max(1).default(0.05),
    alternative: z.enum(['two-sided', 'less', 'greater']).default('two-sided'),
  }),
  preconditions: [
    { id: 'independence', description: '两组样本相互独立', check: 'manual' },
    { id: 'normality_or_n30', description: '近似正态或每组 n≥30', check: 'auto', checkImpl: 'stats.assume.normality' },
  ],
  run: (data, p) => welchTTest(data.groupA, data.groupB, p),   // 指向已验证的库实现
})
```

```ts
// 3) Run manifest：复现的最小充分信息
export type RunManifest = {
  runId: string
  toolId: string
  toolVersion: string
  params: Record<string, unknown>
  inputHash: string                 // 数据文件 sha256
  inputShape: { rows: number; cols: string[] }
  env: { node: string; libs: Record<string, string> }
  preconditionsChecked: Array<{ id: string; passed: boolean; evidence: string }>
  outputs: Array<{ name: string; hash: string }>
  evidence: MethodTool['evidence']  // 一路回指论文
  startedAt: string
  durationMs: number
}
```

**复现的真正含义**：不是"再跑一遍代码"，而是**重放 manifest + 校验输出哈希**。

```bash
$ npm run reproduce -- --run runs/2026-10-26T14-22-01.json
[✓] input hash 匹配
[✓] 环境匹配 (node 24.15.0, scipy 1.14.1)
[✓] 前提假设复检通过 (2/2)
[✓] 输出哈希匹配  p_value=0.0321, effect=0.47
复现成功：与原始运行结果一致
```

这条命令就是需求 B 的最终交付物。它把"复现"从一句口号变成一个可执行的动词。

### 5.4 MCP 暴露

```
mcp-server/
├── server.ts            # 从 registry 自动生成 tool 列表
├── registry.ts          # 读取 tools/*.json 契约
└── tools/*.json         # 每个方法工具的契约（与 TS 实现同源生成）
```

| 约束 | 值 | 理由 |
|---|---|---|
| 暴露的工具数 | ≤ 20 | 超过后模型选择准确率明显下降。源码用 `shouldDefer` + `ToolSearch` 解决，本项目直接控制数量 |
| 工具命名 | `<domain>_<method>` | 与 Claude Code 的 `snake_case` 工具名一致（`arxiv_search`、`stat_test`） |
| 描述 | 必须含「何时用 / 何时不用 / 前提假设」 | 见规范 §5.3 |
| 数据输入 | 只传路径或 hash，不传数据本体 | 避免把表格塞进 context |

**自研 MCP server vs 直接内置工具**：两者都要。MCP server 供外部 agent（Claude Code / 其他客户端）调用，内置工具供本项目主循环调用。**同一个契约、两个适配层**，不要写两份实现。

### 5.5 风险与缓解

| 编号 | 风险 | 触发信号 | 缓解 |
|---|---|---|---|
| R7 | 抽取的"方法"无法映射到基元 | 映射失败率 > 30% | 扩充基元库；仍失败的进入 `unmapped` 队列人工处理，不硬猜 |
| R8 | 前提假设遗漏 → 静默错误结果 | 复现时输出与论文报告值偏离 > 20% | `preconditions` 必填 + 运行前 `auto` 检查 + 偏离超阈值报警而非静默返回 |
| R9 | 术语同名不同义（"归一化"可能是 min-max 或 z-score） | 参数歧义 | 术语表 + 抽取时必须二选一，不允许 `normalize: true` 这种模糊参数 |
| R10 | 工具版本漂移导致旧 manifest 失效 | 复现时 version 不匹配 | toolId 带 semver；minor 变更保证输出兼容；major 变更保留旧实现 |
| R11 | 工具数量膨胀 | > 20 个后模型选错 | 按 domain 分组，同 domain 内合并变体为一个工具 + 枚举参数 |

### 5.6 MVP 定义与验收

**MVP 范围**：15 个分析基元、8 个参数化工具（覆盖「假设检验 / 回归 / 降维聚类 / 数据清洗」四类）、MCP server 可被外部客户端发现、run manifest 可复现。

| 验收项 | 命令 / 动作 | 通过标准 |
|---|---|---|
| 契约完整性 | `npm run tools:validate` | 8 个工具全部通过 JSON Schema 校验，`preconditions` 非空 |
| 可执行 | `npm run tools:smoke` | 8 个工具用样例数据全部跑通 |
| 复现一致 | `npm run reproduce -- --all` | 8 个 manifest 全部复现成功，哈希一致 |
| MCP 可发现 | 外部 MCP 客户端 `list tools` | 看到 8 个工具，描述含触发条件 |
| 溯源 | 任一工具契约 | 有 `paperId + locator + quote`，且 locator 能在 A 中命中 |

## 6. 需求 C · 技能库

### 6.1 可行性结论

| 维度 | 评级 | 说明 |
|---|---|---|
| 技术可行性 | **高** | Skill 是 Markdown + frontmatter，无需可执行代码，Claude Code 已有成熟形态 |
| 工作量（MVP） | 1 天 | 1 个领域、1 个 skill、可被 agent 加载 |
| 主要风险 | 中 | 质量：容易写成"综述摘要"，而非"决策框架"；容易把单篇观点固化成领域共识 |
| 建议 | **做，作为链路的收口** | 它是 A + B 的复用出口，也是演示的最后一环 |

### 6.2 关键判断：Skill 不是综述

这是本需求最容易做错的地方。

| | 综述（Survey） | 技能（Skill） |
|---|---|---|
| 回答的问题 | 这个领域**有什么** | 遇到 X **该怎么做** |
| 结构 | 线性叙事，按主题/时间 | 分层决策框架，按触发条件 |
| 读者 | 人 | agent（以及需要快速上手的人） |
| 长度 | 8000+ 字，越全越好 | 2000 字以内，越可判定越好 |
| 成功标准 | 读完了解了领域 | 加载后能做出**正确决策** |
| 失败形态 | 漏掉重要工作 | 给了错误的判据，导致 agent 自信地做错事 |

**一句话**：综述是知识，skill 是判断力。把综述塞进 skill，agent 会变成一个"话很多但不会做事"的角色。

### 6.3 Skill 结构（照 Claude Code 的 skill 形态裁剪）

```markdown
---
name: econometrics-panel-expert
description: Use when analyzing panel data with fixed effects, testing for
  endogeneity, or choosing between FE / RE / IV estimators. Covers assumption
  checks and common failure modes in applied micro papers.
domain: econometrics
maturity: reviewed          # draft | reviewed | stable
evidence: [arxiv-2401.01234, doi-10.1093/restud/xxx, ...]   # ≥3 篇才允许 reviewed
updated: 2026-10-26
---

## 1. 领域地图（10–20 个节点，不超过 20）
面板数据
├── 估计量选择：FE / RE / FD / IV / GMM
├── 假设检验：Hausman / 过度识别 / 弱工具变量
├── 稳健性：聚类标准误 / 双向聚类 / bootstrap
└── 常见陷阱：动态面板偏误 / Nickell bias / 弱工具

## 2. 标准流程（每个阶段：输入 → 动作 → 判据）
### 阶段 1：数据结构确认
- 输入：长面板 / 宽面板 / 平衡与否
- 动作：调用 `panel_describe`
- 判据：若 T < 5 且模型含滞后项 → 必须用差分 GMM，禁 FE

### 阶段 2：估计量选择
- 先跑 `panel_hausman`；p < 0.05 → FE，否则参考 RE
- 若存在内生性 → 进入 IV 分支（见 `工具映射`）

## 3. 方法 → 工具映射（指向需求 B 的 MCP 工具）
| 场景 | 工具 | 必查前提 |
|---|---|---|
| 静态面板 | `panel_fe` / `panel_re` | 序列相关（`panel_serial_corr`） |
| 动态面板 | `panel_gmm` | 工具变量有效性（`panel_hansen`） |

## 4. 常见失败模式（★ 最有价值的一节）
| 现象 | 可能原因 | 处置 |
|---|---|---|
| 系数符号与理论相反 | 遗漏变量 / 反向因果 | 先做 `panel_endogeneity_check`，不要直接解释系数 |
| 标准误异常小 | 未聚类 | 改用双向聚类，重报 |
| Hansen 检验 p=1.0 | 工具变量过多 | 减少 IV 数量，重估 |

## 5. 术语消歧
- "固定效应"：本文指 entity FE；若论文指 time FE，需显式说明
- "稳健标准误"：默认聚类到个体层，非 White

## 6. 证据索引（指向需求 A 的知识页）
- [[notes/arxiv-2401.01234-nickell-bias]] — 动态面板偏误的量级
- [[notes/doi-10.1093-restud-xxx-fe-consistency]] — FE 一致性条件

## 7. 不要做什么（negative constraints）
- 不要在没有 `panel_serial_corr` 结果时直接报告 FE 标准误
- 不要在 T < 5 时使用系统 GMM
- 不要把单篇论文的偏好表述为领域共识（标 `source: single` 的条目需注明）
```

**七节结构的作用**：§1 建立坐标系，§2 给流程，§3 接工具，§4 给失败判据，§5 消歧，§6 接证据，§7 划边界。其中 **§4 和 §7 是 skill 与综述的分水岭**——只有真正做过这个领域的人（或真正读过足够多论文的 agent）才能写出「什么情况下会错」。

### 6.4 质量门槛：跨论文一致性

**这是防止 C 变成"看起来像专家的胡说"的唯一手段。**

| 规则 | 内容 |
|---|---|
| **三篇规则** | 任何写进「标准做法」的条目，必须能在 ≥3 篇独立论文中找到支持。不足 3 篇的，标注 `source: single` 并写明出处 |
| **矛盾必录** | 论文间冲突的做法不能二选一，必须在 §4 里写成「A 用 X，B 用 Y，判据是 Z」 |
| **可判定性** | §2 每个判据必须是可判定的（`p < 0.05`、`T < 5`），不能是「视情况而定」 |
| **长度上限** | 正文 ≤ 2000 字。超了说明在写综述 |
| **maturity 字段** | `draft`（<3 篇）→ `reviewed`（≥3 篇且人工过）→ `stable`（≥10 篇且被实际使用 5 次以上未修正） |

### 6.5 加载与路由（progressive disclosure）

Agent 不可能一次加载全部 skill。分两级：

```
启动时：只加载所有 skill 的 frontmatter（name + description），约 20 个 × 50 字 = 1000 字
        ↓
模型判断当前任务是否需要某个 skill（只看 description）
        ↓
命中：加载该 skill 全文（≤2000 字）
未命中：不加载，零成本
```

**规则**：`description` 是路由的唯一依据，必须写「**什么时候用**」而不是「这是什么」。这是整个 skill 体系能否规模化的关键——20 个 skill 时无所谓，200 个 skill 时 description 写不好就等于没有。

这与源码的机制完全一致：Claude Code 的 skills 目录加载器只读 frontmatter 做索引（`src/skills/loadSkillsDir.ts`），正文按需注入。

### 6.6 风险与缓解

| 编号 | 风险 | 触发信号 | 缓解 |
|---|---|---|---|
| R12 | 写成综述，agent 不会用 | 正文 > 3000 字、§4/§7 为空 | 结构模板强制七节；§4 少于 5 条打回 |
| R13 | 单篇观点被当共识 | `evidence` < 3 篇却标 `reviewed` | 三篇规则做成校验脚本，CI 拦截 |
| R14 | description 写不清，永不命中 | 20 个领域测试题命中率 < 60% | 用测试题反推 description，迭代到命中 |
| R15 | skill 与工具脱节（指向不存在的工具） | §3 的 toolId 在 B 的 registry 里找不到 | skill 生成时校验 toolId 存在性 |
| R16 | skill 过时（新论文推翻旧结论） | 新入库论文与 skill 条目矛盾 | 入库时做一致性检查，命中则把 skill 标 `stale` 待复核 |

### 6.7 MVP 定义与验收

**MVP 范围**：1 个领域、1 个 skill、正文 ≤ 2000 字、七节齐全、可直接被 Claude Code 作为 skill 加载。

| 验收项 | 命令 / 动作 | 通过标准 |
|---|---|---|
| 结构合规 | `npm run skills:lint` | 七节齐全，§4 ≥ 5 条，正文 ≤ 2000 字 |
| 证据充分 | 同上 | `evidence` ≥ 3 篇，每条 §2 判据有出处 |
| 工具有效 | `npm run skills:lint` | §3 引用的 toolId 全部存在于 B 的 registry |
| 路由准确 | 20 道领域题（10 该命中 + 10 不该命中） | 命中率 ≥ 80%，误命中 ≤ 2 |
| 决策有效 | 5 道"该怎么办"的题，对比无 skill 基线 | 正确答案率提升 ≥ 30% |

> 最后一项是整个项目最有说服力的实验设计：**同一批问题，加载 skill 前后各答一次，报准确率差值**。这比任何定性描述都更能证明 C 的价值。

## 7. 依赖关系与关键路径

```
[底座] PDF 解析 + PaperDoc schema  ★ 冻结于 D1 上午
   │
   ├──► [A] 抽取 → 原子页 → KiwiFS ──────────┐
   │        (D1-D2)                          │
   │                                         ↓
   ├──► [B] 方法抽取 → 基元 → 工具 → MCP    │  C 需要 A 的证据
   │        (D2)          ↑                 │  与 B 的工具
   │                      需要基元库         │
   │                      (D2 上午先写)      │
   │                                         ↓
   └──────────────────────────────────► [C] skill (D3)
                                            │
                                            ↓
                                    [串成一条命令] (D3)
```

**关键路径**：底座 → A → B → C。**B 和 C 并行会互相等待**，因为它们共享「方法」这一概念（B 把方法变工具，C 把方法写进流程）。建议同一人负责 B+C，避免两个人对「方法」的定义不一致。

**最先做的东西**（如果只能做一件）：`PaperDoc` 的 schema。它决定了 A 的原子页能否溯源、B 能否定位参数、C 能否引用证据。

## 8. 交付方案

### 8.1 方案对比

| 方案 | 周期 | 交付内容 | 适合场景 |
|---|---|---|---|
| **方案甲：纵向薄切片** | 4 天 | 一条命令跑通「论文 → 知识页 → 工具 → skill」全链路，每层都是最小可用 | **黑客松演示**。推荐 |
| 方案乙：横向做全 A | 4 天 | 知识库很完整（100 篇、精良 UI），B/C 只有 demo 级占位 | 若目标是"做一个好用的知识库产品" |
| 方案丙：完整版 | 2–3 周 | 三项都达可用，含评测体系 | 比赛后的持续项目 |

**推荐甲，理由**：三项需求的价值在**闭环**，不在单点深度。一个「新论文进来自动长出知识、工具、技能」的 3 分钟演示，比一个「100 篇论文的精美知识库」更能说明这套架构的意义。而且纵向切片能最早暴露三者接口的不一致——这是最大的技术风险。

### 8.2 方案甲：4 天详细计划

#### D1 — 底座与 A 的最小闭环

| 时段 | 任务 | 产出 | 验收 |
|---|---|---|---|
| 上午 | 冻结三份 schema：`PaperDoc` / `AtomicNote` / `MethodTool` + `Skill` frontmatter | `src/types/paper.ts`、`note.ts`、`tool.ts` | 三人 review 一次，之后只加不改 |
| 上午 | 拉 KiwiFS，`kiwifs init` + `kiwifs serve`，验证 multi-space / MCP / Web UI / DQL 四项能力 | 本地跑起来的 space | `curl localhost:3333/api/...` 返回 200 |
| 下午 | PDF → PaperDoc 解析器（先只支持 3 篇样例论文） | `services/pdf/` | 3 篇解析成功，段落带页码 |
| 下午 | 论断抽取 + locator 校验 | `services/extract/` | 3 篇产出 20+ 原子页，`hallucinationRate` 有数字 |
| 收工 | 原子页写入 KiwiFS（REST bulk_write），UI 里能看到 | 可浏览的知识库 | 打开 Web UI 能看到页面与图谱 |

> **D1 的 go/no-go**：如果 KiwiFS 的 multi-space 或 MCP 有阻塞性问题（H1 不成立），当晚必须切换到备选（Obsidian + 自建检索，或本地 Markdown + 简单 FTS），不允许拖到 D2。

#### D2 — A 扩量 + B 最小

| 时段 | 任务 | 产出 | 验收 |
|---|---|---|---|
| 上午 | 基元库：15 个分析函数（假设检验 5 / 回归 4 / 降维聚类 3 / 清洗 3） | `services/primitives/` | 每个有单测，样例数据跑通 |
| 上午 | A 扩到 20 篇，观察 `hallucinationRate`、每篇页数分布 | 质量报告 | 指标写进 `docs/metrics.md` |

## 11. 三份 schema 是唯一的接口

A / B / C 三层的耦合只允许通过三份 schema 发生，禁止跨层直接调函数：

| 接口 | 生产者 | 消费者 | 不允许 |
|---|---|---|---|
| `PaperDoc` | `services/pdf` | A 的抽取器、B 的方法抽取 | B/C 直接读 PDF |
| `AtomicNote` | A 的抽取器 | KiwiFS、C 的 skill 生成器 | C 直接读 KiwiFS 的原始页面 |
| `MethodTool` | B 的工具层 | MCP server、C 的 §3 工具映射 | C 直接调用工具实现 |
| `Skill` | C 的生成器 | agent 加载器 | A/B 直接读 skill 正文 |

**这样做的收益**：任何一层想换实现（例如 KiwiFS 换成别的知识库、PDF 解析换成付费 API），只要保持 schema 不变，其他层零改动。这是 4 天项目里唯一值得做的"架构投资"。

## 12. 风险登记册（汇总）

| 编号 | 风险 | 影响 | 概率 | 优先级 | 主责阶段 |
|---|---|---|---|---|---|
| R1 | 抽取幻觉 | 高（污染 A，传导到 C） | 中 | **P0** | D1 |

| R7 | 方法无法映射基元 | 中（B 缩水） | 中 | P1 | D2 |
| R8 | 前提假设遗漏致静默错误 | **高（最危险）** | 中 | **P0** | D2 |
| R3 | 原子页粒度失控 | 中 | 高 | P1 | D1–D2 |
| R4 | 中文检索效果差 | 中 | 中 | P1 | D1 |
| R12 | skill 写成综述 | 中 | **高** | **P0** | D3 |
| R13 | 单篇观点当共识 | 高（长期资产被污染） | 高 | **P0** | D3 |

## 13. 指标与验收（量化）

文本类项目最容易自我感觉良好，因此必须有硬指标。建议在 D2 就建立 `docs/metrics.md` 看板，每天更新。

| 层 | 指标 | 定义 | 目标（4 天） | 目标（完整版） |
|---|---|---|---|---|
| 底座 | `parseQuality` 中位数 | 成功解析页 / 总页数 | ≥ 0.85 | ≥ 0.95 |
| A | `locatorHitRate` | 抽检 50 页中 locator 能在原文命中的比例 | ≥ 95% | ≥ 98% |
| A | `hallucinationRate` | 校验失败被丢弃的论断 / 抽取总数 | ≤ 10% | ≤ 3% |
| A | `notesPerPaper` | 每篇原子页数 | 6–15 | 6–15 |
| A | 检索 Top-5 命中率 | 10 个已知答案问题的检索准确率 | ≥ 80% | ≥ 90% |
| B | `toolExecutableRate` | 能跑通的工具 / 生成的工具 | 100%（只承诺 8 个） | ≥ 90% |
| B | `reproduceConsistency` | 复现输出哈希一致的比例 | 100% | 100% |
| B | `preconditionCoverage` | 有 auto/manual 检查的前提 / 总前提 | ≥ 80% | 100% |
| C | 路由准确率 | 20 道题中，该加载的加载、不该加载的不加载 | ≥ 80% | ≥ 90% |
| C | skill 增益 | 5 道决策题，加载 skill 前后准确率差值 | ≥ 30 个百分点 | ≥ 40 |
| C | `evidenceCoverage` | §2 判据中带 ≥3 篇证据的比例 | 100%（只做 1 个 skill） | ≥ 80% |

**最值得在答辩时讲的两个数字**：`hallucinationRate`（证明抽取可信）和 **skill 增益**（证明 C 有用）。前者是工程严谨性，后者是产品价值。

## 14. 合规与成本

| 事项 | 说明 | 建议 |
|---|---|---|
| 论文版权 | 全文 PDF 与长段摘录属于受版权保护内容 | 库内只存**元数据 + 短摘录（< 25 词/条）+ 自写复述**；PDF 原文放在 `data/` 不入库、不分发 |
| KiwiFS 许可 | BSL-1.1：可自托管、可修改，**禁止对外提供商业托管服务** | 内部使用与演示无碍；若要对外上线，改用 Apache-2.0 分支或换实现 |
| 数据来源 | arXiv API 有速率限制与使用条款 | 加缓存与退避；遵守 `arxiv.org/robots.txt` |
| LLM 成本 | 100 篇 × 每篇 4 次调用 | 抽取只送当前章节；PaperDoc 落盘复用；批量夜间跑；设单任务预算上限 |
| 隐私 | 论文作者信息、未发表稿 | 不上报任何正文；`SafeForTelemetry` 标注（见规范 §4.4） |

## 16. 一页纸总结

```
三项需求 = 一条流水线
   共享底座（PDF → PaperDoc，带页码锚点）
     ├─ A 知识层：原子知识页 → KiwiFS（多 space + 内置 UI + FTS5/DQL）
     ├─ B 工具层：方法三件套（契约+实现+证据）→ MCP server → run manifest 可复现
     └─ C 技能层：七节结构 skill（判断力，不是综述）→ 按需加载

可行性：A 高 / B 中（分级做，只承诺 L1）/ C 高
4 天策略：纵向薄切片，一条命令贯通，不追求单层深度
唯一架构投资：三份 schema（PaperDoc / AtomicNote / MethodTool）
唯一质量铁律：进入沉淀层的一切信息必须带可验证锚点
最该报的两个数：hallucinationRate、skill 增益
最大的两个陷阱：把切片当成 token chunk（A）、把 skill 写成综述（C）
```

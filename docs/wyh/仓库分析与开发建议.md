## 0. 结论摘要（先看这段）

1. **仓库目前是「规划完整、代码为零」的状态**：9 个受版本控制的文件全部是 Markdown / 模板 / 忽略规则，没有 `package.json`、没有 `src/`、没有一行可执行代码。这是正常起点，但意味着**所有里程碑进度都还是 0%**，四天计划的时间预算尚未真正开始消耗。
2. **最大风险不是技术难度，而是「选题未锁定」这一前置阻塞**：`docs/PLAN.md` 的第 0 节明确要求 D1 上午定选题，但选题未定之前，脚手架、Tool 接口、数据源选型都无法动工。建议把它压缩成一个**有时限的决策点**（D1 12:00），而不是「上午讨论一下」。
3. **建议选 A（PaperAgent）但砍成 A-core**：保留「检索 → 精读 → 提炼 → 结构化产出」主干，砍掉复现代码仓库与 LaTeX 排版，把 C 的「证据表 + PRISMA 流程图」拿来做输出形态。理由与裁剪清单见第 3 节。原参考文档推荐 A 是对的，但它给的是「完整版 A」的工作量，4 天做不完。
4. **`.gitignore` 与 `PLAN.md` 存在一处实际冲突**：`PLAN.md` 要求「可复现的 demo 输入（固定样例，别用现场随机数据）」，而 `.gitignore` 第 34 行的 `data/` 会把任意层级的数据目录连同固定样例一起排除，导致 demo 样例无法入库、无法复现。这是**必须在 D1 修掉**的问题（见 F3）。
5. **缺少「断网也能演示」的设计**：黑客松现场最常见的翻车点是网络与 API 额度。建议从第一天就把 `DEMO_MODE=replay` 的 fixture 回放模式做进工具层，而不是 D4 再补录屏兜底。

综合判断：**基建质量高于同类黑客松仓库的平均水平**（Issue/PR 模板、Conventional Commits、`.gitattributes` 统一换行这些细节通常没人做），真正的短板在「从文档到代码的落地路径」和「演示可靠性设计」——这也正是本文档第 4–9 节的主要内容。

## 2. 关键发现（按影响排序）

### F1 · 计划与执行之间缺少「可执行的接口契约」　影响：高

`PLAN.md` 的 D1 任务写「`Tool` 接口抽象（JSON Schema 描述参数 + 统一执行入口）」，但接口本身没有落成代码或独立文档。多人并行时，每个人对「统一执行入口」的理解会不同，等到 D2 合并时才暴露不一致，返工成本最高。

**动作**：D1 上午由一人独写 `src/tools/types.ts` + `src/agent/types.ts` 并立即合入 `main`，作为**冻结契约**。其余人只依赖这两个文件，不修改它。契约稳定比契约完美重要。

### F2 · 选题未锁定是全局阻塞项　影响：高

三个候选（PaperAgent / LabNotebook / LiteratureSurvey）对应完全不同的工具集与数据源，选错方向等于 D1–D2 白做。`PLAN.md` 已识别这个风险，但只写了「D1 上午必须定」，没有 go/no-go 时点和判断依据。

**动作**：设硬时点 D1 12:00，按第 3 节的检查点执行。**超时未定即默认选 A-core**，不允许把决策拖到下午。

### F3 · `.gitignore` 会吃掉 demo 固定样例　影响：高（低成本可修）

```gitignore
# 当前第 33-37 行
data/
artifacts/
logs/
```

- `data/` 无前导 `/`，会匹配**任意层级**的 `data` 目录，未来 `src/data/`、`tools/data/` 一并被忽略；
- 更关键的是：`PLAN.md` D3 要求「可复现的 demo 输入（固定样例）」，这类样例天然放在 `data/` 或 `fixtures/` 下，结果**无法入库**，队友 clone 后拿不到样例，demo 不可复现。

**动作**：改为根目录锚定 + 显式放行样例：

```gitignore
# 只在仓库根目录忽略易变产物
/data/*
!/data/fixtures/
!/data/README.md
/artifacts/
/logs/
```

同时新增 `fixtures/` 目录并**不**忽略它（API 录制响应、PDF 抽取文本都放这里，见第 7.4 节）。

### F4 · 标签依赖可能导致模板静默失效　影响：中

两份 Issue 模板的 frontmatter 都写了：

```yaml
labels: "type: task, status: todo"
```

GitHub 的行为是：**标签不存在时静默忽略，不报错**。若仓库里还没建 `type: task`、`status: todo`、`type: bug`、`status: in-progress`、`status: review`，那么所有新 Issue 都会是「无标签」状态，`CONTRIBUTING.md` 里「状态只看标签」的整套流程直接失效。附录 B 给出了建议的完整标签清单，可一次性批量创建。

### F5 · 根目录中文加括号文件名是长期地雷　影响：中

`黑客松选题与Claude_Code技术框架(1).md` 同时踩了三个坑：中文、半角括号、根目录放置。括号在 Markdown 链接、shell 命令、URL 中都需要转义；`(1)` 后缀还暗示这是「下载副本」，语义价值为零。

**动作**：迁移为 `docs/reference/claude-code-architecture.md`，同步更新 `README.md` 第 24 行的索引。重命名请用 `git mv` 保留历史。仓库根目录应只留 `README.md`、`CONTRIBUTING.md`、`LICENSE`、`package.json` 这类标准文件。

### F6 · 无 CI，`main` 可跑靠人肉　影响：中

`CONTRIBUTING.md` 反复强调「`main` 随时可跑」「推送后 main 要能跑」，但唯一的保障是人的自觉。4 天项目里 CI 的价值不是「质量门禁」，而是**让「main 挂了」这件事在 3 分钟内被发现**。

**动作**：D1 就加一个极简 workflow（见 8.3 节），只做 `typecheck` + `test` + 一个 fake-LLM 的 loop 冒烟测试，总时长目标 < 90 秒。不要加 lint 格式化门禁——4 天项目里那是纯摩擦。

### F7 · 缺 `.env.example`，onboarding 成本高　影响：中低

`.gitignore` 第 5 行写了 `!.env.example`（放行），但文件不存在。队友拿到仓库后无法知道需要哪些环境变量、哪些必填。

**动作**：建 `.env.example`，把 provider key、model 名、超时、预算上限全部列出来并注明哪些必填。

### F8 · 无架构决策记录，与「学习 Agent 架构」目标有张力　影响：中低

README 写「目标是通过比赛系统学习 Agent 架构开发」。但 4 天后如果只留下代码，没人记得「为什么没用现成 Agent SDK」「为什么记忆用文件而不用向量库」「为什么 compact 用摘要而不是滑窗」。这些恰恰是学习成果本身。

**动作**：不要上 ADR 流程（太重），建单文件 `docs/DECISIONS.md`，一行一条：`日期 | 决策 | 备选方案 | 理由`。每天收工前花 2 分钟补。第 10 节附了建议的首批 5 条决策。

### F9 · 本地分支未推送　影响：低

`wyh` 分支只在本地。若本机出问题或换机器，工作会丢；队友也无法看到「有人在改什么」，与 `CONTRIBUTING.md` 第 5 节「每天收工前分支已 push」冲突。

**动作**：`git push -u origin wyh`。

## 3. 选题建议

### 3.1 三个候选的重新评估

原文的工作量估算采用「核心 / 完整」两档，但**没有定义「核心」到底包含什么**——这是并行开发中最容易失控的模糊点。按「4 天 × 3 人左右」的约束重估：

| 候选 | 原文估时 | 真实关键路径 | 4 天可行性 | 现场观感 |
|---|---|---|---|---|
| A. PaperAgent（完整） | 核心 2–3 d / 完整 4–5 d | PDF 精读（解析质量不可控）→ 代码生成（极易跑偏） | **不可行** | 强 |
| A. PaperAgent（核心） | 2–3 d | 检索 → 抽取 → 综述 | **可行，有余量** | 强 |
| B. LabNotebook | 核心 2 d / 完整 3–4 d | 长任务监控与复现环境 | 可行，**最稳** | 弱（后台任务，现场看不到「在思考」） |
| C. LiteratureSurvey | 核心 3 d / 完整 5 d | 5 阶段 pipeline 串联 | 偏紧，无容错余量 | **最强**（流程图 + 证据表很直观） |

### 3.2 推荐：A-core = A 的骨架 + C 的输出形态

**具体范围（这是「核心」的定义，请写进 Issue）**：

```
输入：一个研究问题（如 "LLM 在低资源语言上的检索增强方法"）
  ↓
[1] 检索    ArxivSearchTool          → 20~30 篇候选（带缓存）
  ↓
[2] 筛选    ScreeningTool            → 按纳入/排除标准留 8~12 篇（记录理由）
  ↓
[3] 精读    PDFReadTool × N（子 Agent 并行）→ 每篇结构化抽取
  ↓
[4] 汇总    SynthesisTool            → 证据表 + 综述草稿 + PRISMA Mermaid 图
  ↓
产出：out/report.md + out/evidence.csv + out/prisma.md
```

**为什么是这个组合**：

- 保留了 A 最核心的学习点（多 agent 并行 + 长文档上下文管理 + 工具抽象），这是「偏工程」团队的目标；
- 用 C 的输出形态替代 A 的「代码复现 + LaTeX 写作」——后者是 A 里最难、最不可控、也最容易在现场跑偏的部分，而「证据表 + PRISMA 图」是**确定性输出**，天然适合演示；
- 精确对应 Claude Code 的三个机制：`AgentTool/runAgent.ts`（并行子 agent）、`services/compact/`（长文档压缩）、`memdir`（已读论文记忆），README 里「借鉴了什么」有实打实的内容可讲。

**明确砍掉（写进 README「未做范围」一节，主动交代比被问出来好）**：

| 砍掉 | 理由 |
|---|---|
| 复现代码骨架（`CodeScaffoldTool`） | 生成质量不可控，失败即毁 demo |
| LaTeX 排版 | 无人在 3 分钟内分辨 `.tex` 与 `.md` 的差别 |
| 引用图谱（`CitationGraphTool`） | 增值低、API 调用成本高 |
| 多语言输出 | 纯锦上添花 |
| 完整 PDF 图表/表格精读 | 解析成功率的方差太大 |

### 3.3 决策检查点（D1 12:00 go/no-go）

| 时点 | 检查项 | 未通过则 |
|---|---|---|
| D1 10:00 | 三个人各用自己的 key 成功调通一次 LLM API | 立刻换 provider（这是最致命的外部依赖） |
| D1 12:00 | 选题锁定 + Milestone 建好 + D2 任务拆成 Issue | **默认选 A-core**，不再讨论 |
| D2 17:00 | 3 个工具中至少 2 个能对真实数据返回结果 | 砍掉子 Agent，退化为单 agent 多工具（PLAN.md 已有此预案，提前到 D2 下午执行） |
| D3 17:00 | `bash scripts/demo.sh` 能一条命令产出终稿 | 冻结新功能，全部人力转 demo 稳定性 |

## 4. 技术选型建议

### 4.1 推荐栈

| 维度 | 建议 | 理由 |
|---|---|---|
| 语言 | TypeScript | Tool 接口 + JSON Schema + `tool_use` 结构化解析，类型系统能省掉大量运行时调试；也是 Claude Code 本身的形态，对照学习成本最低 |
| 运行时 | Node 24（团队已确认 `v24.15.0`） | 见 4.2，可省掉构建步骤 |
| 包管理 | pnpm（或 npm，**不要两样都用**） | 4 天项目里选团队最熟的那个，别为工具链争论 |
| LLM API | `@anthropic-ai/sdk` | 见 4.3，只用它的 API 客户端 |
| 参数校验 | `zod` + `zod-to-json-schema` | 一处定义，同时产出 JSON Schema 与运行时校验，避免 schema 与代码不同步 |
| 终端 UI | `chalk` + `ora`（或原生 `process.stdout`） | 不要上 Ink/React——4 天项目里 UI 框架是纯负债 |
| 测试 | Node 内置 `node:test` | 零依赖、零配置，`node --test` 直接跑 |
| 日志 | 自写 JSONL trace（见 7.3） | 比任何日志库都更适合「回放与演示」 |

### 4.2 一个可能省下半天的小验证

Node 22.18+ / 24 已默认支持**直接执行 TypeScript**（类型剥离，无需 `tsc` / `tsx` / `ts-node`）。建议 D1 花 10 分钟验证：

```bash
node --version                  # 需 >= 22.18
echo 'const x: number = 1; console.log(x)' > /tmp/t.ts && node /tmp/t.ts
```

能跑通就直接 `node src/main.ts`，**省掉整个构建配置**；只需要保留 `tsconfig.json` 做类型检查（`tsc --noEmit`，进 CI）。限制是：不能用 `enum` / `namespace` / 构造函数参数属性，import 需带扩展名——对 4 天项目完全不是负担。

若失败则退回 `tsx`（`npx tsx src/main.ts`），成本也就一行。

### 4.3 关键取舍：SDK 用到哪一层

这是整个项目最值得明确的一条技术决策：

| 方案 | 得到什么 | 失去什么 | 结论 |
|---|---|---|---|
| 用 Claude Agent SDK 全家桶 | 一天就有能跑的东西 | **学不到主循环**——而主循环正是本次比赛的核心学习目标 | 否决 |
| 从零手写 HTTP + SSE | 完全掌控 | 浪费 1 天在流式解析和重试上 | 否决 |
| **用 SDK 的 API 客户端 + 自写 agent 循环** | 既不用碰 HTTP 细节，又完整实现「调 LLM → 解析 tool_use → 执行 → 回填 → 再调用」 | 需要自己处理 tool_use 累积与回填顺序 | **采纳** |

一句话原则：**「用 SDK 的客户端，不用 SDK 的循环」**。请把这条写进 `DECISIONS.md` 和 README，答辩时是加分项。

### 4.4 Provider 与降级

`PLAN.md` 已识别「提前测通 2 个 provider」，建议具体化为：

| 优先级 | Provider | 用途 |
|---|---|---|
| 主 | Anthropic 官方（模型可配） | 全部开发与演示 |
| 备 | 任一 OpenAI 兼容端点（OpenRouter / 国内代理 / Kimi / Qwen） | 主挂时切换 |
| 终极兜底 | `DEMO_MODE=replay`（读 fixture，不调 API） | **断网演示** |

抽象一层即可，不要过度设计：

```ts
// src/llm/client.ts
export interface LLMClient {
  create(req: LLMRequest): Promise<LLMResponse>;  // 非流式先跑通
  stream(req: LLMRequest): AsyncIterable<LLMEvent>; // D3 再做
}
```

**建议先只实现非流式**。流式对「跑通链路」没有贡献，只是观感；把它放到 D3，且做成可开关（`--stream`）。很多人在这里陷进去半天，然后发现 token 累积逻辑写错了。

## 5. 架构建议

### 5.1 目录结构

```
hackathon-agent/
├── src/
│   ├── main.ts                  # 入口：CLI 参数 → 装配 → run
│   ├── config.ts                # 环境变量、模型、预算、超时（单点真相）
│   ├── agent/
```

### 5.2 分层职责与依赖方向

```
main.ts ──► agent/loop.ts ──► llm/client.ts
                │
                ├──► tools/registry.ts ──► tools/*.ts ──► (外部 API | fixtures)

                ├──► context/compact.ts
                ├──► memory/store.ts
                └──► obs/trace.ts
```

铁律：**工具不允许调用 LLM，循环不允许知道具体工具名**。工具是纯函数式的「外部世界适配器」，所有决策都在循环里。这条守住了，D3 集成时不会出现「不知道谁在调谁」。

### 5.3 一次完整请求的数据流

```
user task
   ↓
loop: messages = [{role:user, content: task}]
   ↓
llm.create({ system, messages, tools })
   ↓
resp.content = [ text?, tool_use×N ]
   ↓  无 tool_use → 返回文本，结束
assistant message 入栈
   ↓
for each tool_use（可并行）:
    registry.execute()
      ├ 查 tool 是否存在         → 不存在则返回结构化错误
      ├ zod 校验入参             → 失败则返回结构化错误（让模型自己修）
      ├ 权限/白名单检查
      ├ cache 命中？
      ├ 超时/异常捕获            → 永不 throw 到循环外
      └ trace 记录
   ↓
全部 tool_result 按原顺序合成**一条** user message 入栈
   ↓
预算/轮数检查 ──► 回到 llm.create
```

## 6. 核心接口设计

### 6.1 Tool 契约

```ts
// src/tools/types.ts
import type { ZodType } from 'zod';

export interface ToolContext {
  signal: AbortSignal;              // 贯穿全链路的取消
  trace: (event: Record<string, unknown>) => void;
  cache: { get<T>(k: string): Promise<T | undefined>; set<T>(k: string, v: T): Promise<void> };
  workdir: string;
}

export interface ToolResult<O = unknown> {
  ok: boolean;
  data?: O;
  error?: { code: string; message: string; hint?: string }; // hint 会回填给模型，让它自我修正
  meta: { tool: string; ms: number; cached: boolean };
}

export interface Tool<I = unknown, O = unknown> {
  name: string;                     // snake_case，模型友好
  description: string;              // 写清「什么时候该用」，不是「它是什么」
  schema: ZodType<I>;               // 单一真相：同时产出 JSON Schema 与运行时校验
  readOnly: boolean;                // 只读工具可并行、可缓存、免确认
  timeoutMs?: number;               // 默认 30_000
  call(input: I, ctx: ToolContext): Promise<O>;
}
```

两个容易做错的地方：

1. **`hint` 字段**。工具失败时给模型一句可操作的提示（例如「该论文 ID 不存在，请先用 arxiv_search 获取合法 ID」），比抛一句 `404` 的转化率高得多。这是「错误处理不炸主循环」真正有价值的形态——不只是不崩，而是**能自愈**。
2. **`description` 写触发条件**。模型选错工具的原因 90% 是 description 写成了功能描述（「搜索 arXiv」）而不是使用条件（「当需要按关键词查找论文、且尚无论文 ID 时使用」）。

### 6.2 主循环骨架

```ts
// src/agent/loop.ts
export async function runAgent(opts: RunAgentOptions): Promise<RunResult> {
  const messages: Message[] = [{ role: 'user', content: opts.task }];
  let turn = 0;

  while (turn++ < opts.budget.maxTurns) {
    const resp = await opts.llm.create({
      system: opts.system,
      messages,
      tools: opts.registry.schemas(),
    });

    opts.budget.charge(resp.usage);

    const toolUses = resp.content.filter(isToolUse);
    if (toolUses.length === 0) {
      return { text: textOf(resp.content), turns: turn, usage: opts.budget.snapshot() };
    }

    messages.push({ role: 'assistant', content: resp.content });

    // 只读工具可并行；有副作用的串行
    const results = await opts.registry.executeAll(toolUses, ctx);

    // 关键：全部 tool_result 合成一条 user message，顺序必须与 tool_use 一致
    messages.push({ role: 'user', content: results });

    if (opts.budget.exceeded()) break;
    if (opts.compact.shouldCompact(messages)) {
      messages = await opts.compact.apply(messages);
    }
  }
  throw new BudgetExceededError(opts.budget.snapshot());
}
```

**必须记住的两个协议细节**（不记住会浪费一小时排查）：

- 一条 assistant message 里可能有多条 `tool_use`，其对应的 `tool_result` 必须**全部**放在**下一条** user message 里，且 `tool_use_id` 一一对应；漏掉任何一个，API 会直接 400。
- 流式模式下，`input_json_delta` 是**分片字符串**，需要按 `index` 累积拼接后再 `JSON.parse`，不能逐片解析。

### 6.3 子 Agent

```ts
// src/agent/subagent.ts
export async function runSubagent(spec: {
  name: string;
  task: string;
  tools: string[];                  // 工具白名单，不是全量
  maxTurns?: number;
  parent: AgentContext;
}): Promise<SubagentResult> {
  const registry = parent.registry.subset(spec.tools);   // 关键：白名单裁剪
  const ctx = parent.fork({                            // 独立上下文、独立 trace 前缀
    tracePrefix: `${parent.tracePrefix}/${spec.name}`,
    budget: parent.budget.child(0.3),                  // 子 Agent 预算上限，防跑飞
  });
  const res = await runAgent({ task: spec.task, registry, ...ctx });
  return { name: spec.name, text: res.text, usage: res.usage }; // 只回填摘要，不回填完整消息
}
```

三个要点：

- **只回填结论**。子 Agent 的完整对话留在自己的上下文里，父上下文只收一段摘要——这正是 Claude Code 子 Agent 机制的精髓，也是长文档不炸上下文的唯一原因。
- **白名单最小化**。`ReadAgent` 只能拿到 `pdf_read`，不能有 `arxiv_search`。
- **并行 + 失败隔离**。8 篇论文并行精读，单篇失败返回「本篇失败」而不是整体失败；父 Agent 决定是否重试。

### 6.4 cache-first 工具（保障演示的第二道保险）

```ts
// src/tools/cache.ts
export function withCache<I, O>(tool: Tool<I, O>): Tool<I, O> {
  return {
    ...tool,
    async call(input, ctx) {
      const key = `${tool.name}:${sha1(stableStringify(input))}`;
      if (ctx.env.CACHE_MODE !== 'off') {
        const hit = await ctx.cache.get<O>(key);
        if (hit !== undefined) return hit;
      }
      const out = await tool.call(input, ctx);
      await ctx.cache.set(key, out);          // 成功后落盘到 fixtures/
      return out;
    },
  };
}
```

`CACHE_MODE=off | read | readwrite`（默认 `readwrite`）。开发期第一次真实调用后结果自动落进 `fixtures/`，**从那一刻起 demo 就与网络解耦了**。这是本文档认为 ROI 最高的一段代码，约 20 行，建议 D2 就加。

## 7. 健壮性与成本控制

### 7.1 硬约束清单（全部塞进 `config.ts`）

| 约束 | 建议值 | 为什么必须有 |
|---|---|---|
| 单次工具超时 | 30 s（PDF 解析 120 s） | 一个卡死的 HTTP 请求能让整个 demo 停住 |
| 主循环最大轮数 | 25 | 模型会陷入「反复搜索同一关键词」的死循环 |
| 单次任务 token 预算 | 可配，默认按 provider 定价折算成金额上限 | 长文档场景极易一夜烧掉额度 |
| 单次任务时间上限 | 10 min | 演示不可能等更久 |
| LLM 重试 | 3 次，指数退避 + 抖动，仅对 429/5xx/网络错误 | 不要对 400（参数错）重试，那是 bug 不是抖动 |
| 子 Agent 并发上限 | 3–4 | 并发太高直接触发 provider 限流 |

### 7.2 「不炸主循环」的正确姿势

```ts
// src/tools/registry.ts
async executeAll(uses: ToolUse[], ctx: ToolContext): Promise<ToolResultBlock[]> {
  return Promise.all(uses.map(async (u) => {
    try {
      return await this.withTimeout(this.executeOne(u, ctx), u);
    } catch (e) {
      return this.failureBlock(u, e);   // 结构化错误，不是异常
    }
  }));
}
```

规则：**循环层永不 catch，工具层永不 throw**。所有异常在 registry 边界转成 `ToolResult`。这样「工具失败」对模型而言只是一条信息，它有机会自己换策略。

### 7.3 JSONL trace + replay

每轮记录一条 JSONL，字段最小化：`ts, turn, event, tool, inputHash, ok, ms, usage`。

价值有三个，且都不能靠「事后补」实现：

1. **调试**：多 Agent 并行时终端输出会交错，日志是唯一可信的时间线；
2. **演示兜底**：`DEMO_MODE=replay` 直接按 trace 重放终稿，断网也能演；
3. **答辩素材**：「本次运行 12 轮、37 次工具调用、消耗 X token、耗时 4 分 20 秒」——比任何 PPT 都有说服力。

### 7.4 上下文管理（长文档的必修课）

`PLAN.md` 已把它列为 D3 的事，建议提前到 **D2 下午**，因为它是「8 篇论文」能否跑通的前提。

| 策略 | 做法 | 用在哪 |
|---|---|---|
| 分而治之（首选） | 每篇论文交给独立子 Agent，父上下文只收 300 字摘要 | 论文精读 |
| 分段摘要 | 长文本按章节切块，逐块摘要，再对摘要摘要 | 单篇超长 PDF |
| 结构化压缩 | 抽取固定字段（method / dataset / result / limitation）而非自由摘要 | 证据表生成 |
| 滑窗 | **不要用**——会丢掉早期关键信息，且不可解释 | — |

注意一个陷阱：`compact` 会破坏 prompt cache（如果 provider 支持）。4 天项目里不必为此优化，但要知道自己在付出什么。

### 8.1 把验收标准写成可执行命令

`PLAN.md` 的验收标准是定性的（「主循环能完成至少 1 轮」），建议替换成可执行的：

| 里程碑 | 验收命令 | 通过标准 |
|---|---|---|
| M1 骨架 | `npm test` | `loop.test.ts` 用 FakeLLM 跑通：1 条 tool_use → 1 条 tool_result → 文本结束，消息序列断言通过 |
| M1 骨架 | `node src/main.ts --task "用一句话说明你是谁"` | 终端打印文本 + 至少 1 条 trace |
| M2 工具 | `node src/main.ts --task "搜索 RAG 相关论文 3 篇"` | `artifacts/` 下出现 3 条论文 JSON，trace 中工具耗时可见 |
| M3 端到端 | `bash scripts/demo.sh` | `out/report.md`、`out/evidence.csv`、`out/prisma.md` 三件产物齐备 |
| M4 断网 | `DEMO_MODE=replay bash scripts/demo.sh` | **整个过程不发起任何网络请求**（可临时拔网线验证） |

最后一条是整个测试体系的核心。**「断网也能跑」是一个二值标准**，比「跑起来还算流畅」可验证得多。

### 8.2 三个人该写什么测试

不需要追求覆盖率，只写三类：

| 类型 | 数量 | 例子 |
|---|---|---|
| 契约测试 | 3–4 个 | tool schema 校验失败时的返回形状；未知工具名 |
| 循环测试 | 2–3 个 | 多 tool_use 并行 → 顺序回填；预算耗尽抛错 |
| 回归测试 | 每修一个 demo 阻塞型 bug 加 1 个 | 之前炸过的那条路径 |

用 `FakeLLM`（返回预置 `content` 的实现）就能覆盖前两类，无需真实 API、无需网络、毫秒级完成。这是让 CI 有意义的唯一方式。

## 11. 风险再评估

`PLAN.md` 第 3 节的风险表已覆盖 API 不稳、上下文炸、网络、并行冲突。以下四条是它没覆盖、但更可能发生的：

| 新增风险 | 触发信号 | 预案 |
|---|---|---|
| **PDF 解析质量不可控** | 抽取出的字段有大段乱码或空值 | PDF 降级为「摘要文本」——arXiv 元数据自带 abstract，多数提炼任务不读全文也够。**这条降级路径要在 D2 就设计好**，不要等失败 |
| **模型不按 schema 输出** | 抽取字段类型错、缺必填 | zod 校验失败 → 把错误信息与 schema 一起回填，让它重试一次；重试仍失败则标记该篇「抽取失败」并继续。绝不让单篇阻塞全局 |
| **range creep（范围蔓延）** | 有人在 D3 说「顺便加个引用图谱吧」 | D3 17:00 冻结线，之后新需求一律进 `backlog` 标签，不合入 |
| **集成地狱（三人分支互相不兼容）** | D2 下午出现大量冲突 | 契约层（`types.ts`）已冻结 + 每人一个 `tools/*.ts` 文件 + 每日 main 可跑。**文件级分工是唯一有效的手段**，不要靠沟通解决 |

## 附录 C · 与 Claude Code 机制的对照

答辩时这张表是最有价值的输出，`PLAN.md` M4 也要求 README 讲清这一点：

| 本项目模块 | 借鉴自 | 借鉴了什么 | 简化了什么 |
|---|---|---|---|
| `agent/loop.ts` | `src/query.ts` | tool_use 循环、结果回填、循环上限 | 无中断恢复、无权限模式切换 |
| `tools/types.ts` | `src/Tool.ts` | JSON Schema 驱动 + 统一执行入口 | 无进度流、无 diff 渲染 |
| `agent/subagent.ts` | `AgentTool/runAgent.ts` | 独立上下文 + 工具白名单 + 只回填摘要 | 无 fork 会话、无跨 Agent 记忆共享 |
| `context/compact.ts` | `services/compact/` | 长历史摘要 | 无自动触发策略调优 |
| `memory/store.ts` | `src/memdir/` | 文件式持久化 + 可读可改 | 无自动抽取、无 USER/PROJECT 双域 |
| `obs/trace.ts` + `tools/cache.ts` | — | **原创**（针对 demo 可靠性） | — |

最后一行值得强调：**「为了在现场可信地演示，我们给工具层做了可注入的缓存与回放」**，这是一个 Claude Code 里没有、但在黑客松场景下真正解决问题的设计。答辩讲这个，比复述别人的架构更有分量。

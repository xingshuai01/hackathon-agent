## 0. 三条总原则

源码里能反复观察到的、比任何具体规则都重要的三件事：

**原则一：契约集中在少数文件里，其余全部依赖契约。**
`src/Tool.ts`（792 行）定义了全部 40+ 工具的形状，`src/tools.ts`、`src/commands.ts` 是唯一的注册中心。工具实现只 `satisfies` 契约，从不修改契约。

**原则二：默认值 fail-closed，能力靠显式声明。**
`buildTool` 的默认值是"不安全"的：`isConcurrencySafe → false`、`isReadOnly → false`、`isDestructive → false`。你必须在实现里主动声明"我是只读的"，框架从不替你假设安全。

**原则三：错误是数据，不是控制流。**
工具失败返回 `{result: false, message, errorCode}` 这样的可判定对象（`src/Tool.ts:95`），异常只在真正不可恢复处抛出，且全局有 `isAbortError`/`isENOENT` 这类守卫函数做类型收窄（`src/utils/errors.ts`）。

> 三条原则对应到本项目：**先把 `Tool` 与消息类型冻结，再写工具；所有工具默认不可并发、不可写；工具层永不 throw**。

## 1. 目录与模块边界

### 1.1 分层结构

源码的 `src/` 根目录是**按职责平铺**的，不按"功能模块"嵌套：

```
src/
├── main.tsx        入口
├── Tool.ts         ★ 契约：工具类型
├── tools.ts        ★ 注册表：工具清单
├── commands.ts     ★ 注册表：命令清单
├── query.ts        ★ 主循环
├── QueryEngine.ts  循环的对外封装
├── context.ts      上下文收集
├── cost-tracker.ts 成本追踪
├── tools/          40+ 工具，一目录一工具
├── commands/       50+ 斜杠命令
├── services/       外部服务：api / mcp / compact / extractMemories
├── utils/          329 个纯函数模块
├── types/          跨模块共享类型
├── constants/      常量：toolLimits / errorIds / apiLimits
└── components/     UI（Ink）
```

**规则 1.1**：一个模块只在**一个**层级里出现。工具不放在 `services/` 下，服务不放在 `tools/` 下。
**规则 1.2**：跨模块共享的类型必须下沉到 `types/`，不在两个业务模块间互相 import 类型。
**规则 1.3**：常量放 `constants/`，且按域拆文件（`toolLimits.ts`、`errorIds.ts`），不建 `constants.ts` 大杂烩。

出处：`src/` 根目录清单；`src/constants/` 下 20 个按域拆分的文件。

### 1.2 一个工具 = 一个目录

这是源码里最值得照搬的结构。以最简单的 `GlobTool` 为例：

```
tools/GlobTool/
├── GlobTool.ts   实现（6064 字节）
├── prompt.ts     工具名常量 + 描述文案（439 字节）
└── UI.tsx        渲染函数（8040 字节）
```

**规则 1.4**：工具目录内固定三类文件：

| 文件 | 职责 | 是否必需 |
|---|---|---|
| `XxxTool.ts` | `buildTool({...})` 实现，唯一导出 | 必需 |
| `prompt.ts` | 工具名常量（`GLOB_TOOL_NAME`）+ 描述文案 | 必需 |
| `UI.tsx` | 渲染函数（终端输出） | 必需（本项目可简化为 `UI.ts`） |
| `constants.ts` | 仅当该工具有多个入口需要共享常量时 | 可选 |

**为什么要拆 `prompt.ts`**：工具名被注册表、权限规则、另一工具的提示词三处引用，散落成字面量就会出现"改名后某一处失效"。源码里 `AgentTool/constants.ts` 的 `AGENT_TOOL_NAME` 甚至被其他工具的 prompt 模板 import（见 `src/skills/bundled/simplify.ts:1`）——**prompt 是代码，常量必须单一来源**。

## 2. 命名规范

| 对象 | 规则 | 源码实例 |
|---|---|---|
| 目录（工具） | PascalCase + `Tool` 后缀 | `tools/GlobTool/`、`tools/FileReadTool/` |
| 文件（模块） | camelCase | `query.ts`、`tokenBudget.ts`、`autoCompact.ts` |
| 文件（React 组件） | PascalCase + `.tsx` | `CompanionSprite.tsx` |
| 文件（类型） | camelCase，单数 | `types/message.ts`、`types/permissions.ts` |
| 类型 / 接口 | PascalCase，无 `I` 前缀 | `ToolUseContext`、`ToolResult`、`PermissionResult` |
| 值 / 函数 | camelCase，动词开头 | `findToolByName`、`createUserMessage`、`checkTokenBudget` |
| 常量（导出） | SCREAMING_SNAKE | `MAX_ENTRYPOINT_LINES`、`PROMPT_TOO_LONG_ERROR_MESSAGE` |
| 工具名常量 | SCREAMING_SNAKE + `_TOOL_NAME` | `GLOB_TOOL_NAME`、`AGENT_TOOL_NAME` |
| 布尔函数 | `is` / `has` / `should` / `can` 前缀 | `isENOENT`、`isConcurrencySafe`、`hasEmbeddedSearchTools`、`shouldDefer` |

**规则 2.2**：布尔字段用肯定式，`isEnabled` 而非 `isDisabled`（源码 `Tool.isEnabled`、`Tool.isEnabled()`）。
**规则 2.3**：单位进名字。`timeoutMs`、`maxResultSizeChars`、`durationMs`——源码里凡数值必有单位后缀。

## 3. 导入规范

源码的 import 顺序是**手工维护**的，不是在按字母排序（`src/tools.ts:1` 明确用 `biome-ignore` 禁止重排）：

```ts
// 1) 外部包（type-only 优先）
import type { ToolResultBlockParam, ToolUseBlockParam } from '@anthropic-ai/sdk/resources/index.mjs'
import type { z } from 'zod/v4'

// 2) 本包的契约层
import type { Tool, Tools } from './Tool.js'

// 3) 业务模块
import { checkReadPermissionForTool } from './utils/permissions/filesystem.js'

// 4) 同目录
import { DESCRIPTION, GLOB_TOOL_NAME } from './prompt.js'
```

**规则 3.1**：相对导入**必须带 `.js` 扩展名**（ESM/NodeNext 要求），即便源文件是 `.ts`。全仓无一例外。
**规则 3.2**：纯类型导入必须用 `import type`，与值导入严格分离。源码里 `import type {...}` 占 import 语句的相当比例。
**规则 3.3**：分组之间空一行，组内按"外部 → 契约 → 业务 → 同目录"排列，**新增导入 append 到所属组末尾，不重排整块**（避免无意义 diff）。
**规则 3.4**：循环依赖用函数式懒加载打破，不用重构绕。源码标准写法：

```ts
// src/tools.ts:61  —— 注释说明了为什么必须这样
// Lazy require to break circular dependency: tools.ts -> TeamCreateTool -> ... -> tools.ts
const getTeamCreateTool = () =>
  require('./tools/TeamCreateTool/TeamCreateTool.js')
    .TeamCreateTool as typeof import('./tools/TeamCreateTool/TeamCreateTool.js').TeamCreateTool
```

注意这里的 `as typeof import(...)` 是必需的——`require` 拿不到类型，必须用 `import()` 类型查询补回来。
**规则 3.5**：不要建 barrel file（`index.ts` 全量再导出）。源码的 `services/*/index.ts` 只做聚合入口，不做"把目录下所有东西都导出"。

出处：`src/Tool.ts:1-88`、`src/tools.ts:1-73`、`src/tools/GlobTool/GlobTool.ts:1-24`。

## 4. 类型与 Schema 规范

### 4.1 Zod 是唯一真相

源码不写"手写 TS 类型 + 手写 JSON Schema"，而是**只写 Zod schema，其余全部推导**：

```ts
// src/tools/GlobTool/GlobTool.ts:26-55
const inputSchema = lazySchema(() =>
  z.strictObject({
    pattern: z.string().describe('The glob pattern to match files against'),
    path: z.string().optional().describe(
      'The directory to search in. If not specified, the current working directory will be used. IMPORTANT: Omit this field to use the default directory. DO NOT enter "undefined" or "null" - simply omit it for the default behavior.',
    ),
  }),
)
type InputSchema = ReturnType<typeof inputSchema>

const outputSchema = lazySchema(() => z.object({ ... }))
type OutputSchema = ReturnType<typeof outputSchema>
export type Output = z.infer<OutputSchema>
```

**规则 4.1**：输入 schema 用 `z.strictObject`，输出用 `z.object`。输入严格（拒绝多余字段，模型幻觉出的参数会立刻暴露），输出宽松（向后兼容）。
**规则 4.2**：每个字段必须 `.describe()`，且描述**写给模型看**——写清类型、是否可选、边界条件、常见错误。反例：`describe('路径')`。正例见上，连"不要传字符串 undefined"都写进去了，因为模型真的会这么干。
**规则 4.3**：schema 一律用 `lazySchema()` 包裹，通过 getter 暴露：

```ts
get inputSchema(): InputSchema { return inputSchema() }
```

`lazySchema` 的实现只有 5 行（`src/utils/lazySchema.ts`），作用是把 Zod 构造从模块加载期推迟到首次访问期。40+ 工具 + 50+ 命令全量构造 Zod 会造成明显的启动开销。
**规则 4.4**：类型从 schema 推导（`z.infer<typeof X>`），不手写重复的 interface。
**规则 4.5**：输出类型显式导出（`export type Output`），供 `mapToolResultToToolResultBlockParam` 使用。

### 4.2 可判定结果是联合类型，不是布尔 + 可选字段

```ts
// src/Tool.ts:95
export type ValidationResult =
  | { result: true }
  | { result: false; message: string; errorCode: number }
```

**规则 4.6**：凡"成功/失败带不同载荷"的场景，用 discriminated union，不用 `{ ok: boolean; data?: T; error?: string }`。后者允许 `ok:false` 却没有 `error` 这种非法状态存在。

### 4.3 收窄而不是断言

**规则 4.7**：`catch` 的参数一律标注 `catch (e: unknown)`，然后用守卫函数收窄：

```ts
// src/tools/GlobTool/GlobTool.ts:106-122
let stats
try {
  stats = await fs.stat(absolutePath)
} catch (e: unknown) {
  if (isENOENT(e)) {
    const cwdSuggestion = await suggestPathUnderCwd(absolutePath)
    let message = `Directory does not exist: ${path}. ${FILE_NOT_FOUND_CWD_NOTE} ${getCwd()}.`
    if (cwdSuggestion) message += ` Did you mean ${cwdSuggestion}?`
    return { result: false, message, errorCode: 1 }
  }
  throw e          // 不认识的错误原样上抛，不吞
}
```

注意三个细节：`e: unknown`、只处理认识的错误、其余 `throw e` 而不是转成通用错误。

**规则 4.8**：禁止 `as any`。`as` 只能用于两处：`as const`、以及类型系统无法表达但运行时已验证的桥接（如 `src/Tool.ts:787` 的 `buildTool` 返回，且有注释说明"60+ 工具零类型错误已证明")。

### 4.4 品牌类型保护敏感数据

源码里有一个值得学的做法：把"不能进日志"的字符串做成品牌类型，**从类型层面阻断误用**：

```ts
// 出现在 src/query.ts、src/memdir/memdir.ts 等处
import type { AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS } from './services/analytics/index.js'
```

这个类型名本身就是一道强制审阅门：想往分析事件里塞数据，必须显式写下"我确认这不是代码或文件路径"。

**规则 4.9**：本项目把它简化为 `SafeForTelemetry`，用于一切上报/日志字段。

出处：`src/Tool.ts:15-21,95-101,343`、`src/tools/GlobTool/GlobTool.ts`、`src/utils/lazySchema.ts`、`src/utils/errors.ts`。

## 5. 工具定义规范（核心章节）

### 5.1 必须走 `buildTool`

**规则 5.1**：任何工具都以 `buildTool({...})` 创建，不允许手写完整 `Tool` 对象。

```ts
export const GlobTool = buildTool({
  name: GLOB_TOOL_NAME,
  // ...
} satisfies ToolDef<InputSchema, Output>)
```

源码理由写在 `src/Tool.ts:743-793`：默认值集中在一处，调用方永远不需要 `?.() ?? default`。且 `buildTool` 的返回类型 `BuiltTool<D>` 做了类型级展开，保证"缺省的方法在返回类型里是必有的"——调用侧不需要判空。

### 5.2 必须实现的六个成员

源码的 `Tool` 有 40+ 个成员，但**真正每个工具都实现的核心只有六个**。以下是本项目需要的裁剪版契约：

```ts
// src/Tool.ts（本项目版）
export type Tool<Input extends AnyObject = AnyObject, Output = unknown> = {
  readonly name: string
  readonly inputSchema: Input
  /** 返回给模型的工具说明（含使用条件），不是给用户看的 */
  prompt(): Promise<string>
  /** 执行。永不 throw，失败返回 data 中的错误结构 */
  call(
    args: z.infer<Input>,
    context: ToolUseContext,
    onProgress?: ToolCallProgress,
  ): Promise<ToolResult<Output>>
  /** 序列化为 API 的 tool_result block */
  mapToolResultToToolResultBlockParam(content: Output, toolUseID: string): ToolResultBlockParam
  isConcurrencySafe(input: z.infer<Input>): boolean
  isReadOnly(input: z.infer<Input>): boolean
  // 由 buildTool 提供默认值：isEnabled / isDestructive / userFacingName
}
```

| 成员 | 默认值 | 本项目是否保留 |
|---|---|---|
| `call` | 无默认，必需 | 保留 |
| `prompt` | 无默认，必需 | 保留 |
| `mapToolResultToToolResultBlockParam` | 无默认，必需 | 保留 |
| `isConcurrencySafe` | `false` | 保留（决定能否并行） |
| `isReadOnly` | `false` | 保留（决定能否缓存） |
| `isEnabled` | `true` | 保留 |
| `isDestructive` | `false` | 保留（决定是否需人工确认） |
| `validateInput` | 无 | 保留（前置校验，返回 `ValidationResult`） |
| `renderToolResultMessage` 等 20+ 个 UI 方法 | 无 | **裁剪**（本项目用极简终端输出） |
| `extractSearchText` / `isSearchOrReadCommand` / `toAutoClassifierInput` | 无 | **裁剪**（服务于源码的 UI 折叠与安全分类器） |
| `interruptBehavior` / `requiresUserInteraction` / `shouldDefer` | 无 | **裁剪** |

**规则 5.2**：只保留"影响运行时行为"的成员，UI 类成员一个都不要。源码那 20 多个 render 方法服务于一个成熟 TUI 产品，4 天项目照抄等于自杀。

### 5.3 工具实现的完整范式

```ts
// src/tools/ArxivSearchTool/prompt.ts
export const ARXIV_SEARCH_TOOL_NAME = 'arxiv_search'
export const DESCRIPTION = `Search arXiv for papers matching a query.

When to use:
- You need to find papers by keyword/topic and do not yet have paper IDs.
- You need the canonical metadata (title, authors, year, abstract) of a paper.

When NOT to use:
- You already have an arXiv ID — read it directly instead.`
```

```ts
// src/tools/ArxivSearchTool/ArxivSearchTool.ts
import { z } from 'zod/v4'
import { buildTool, type Tool, type ToolDef, type ValidationResult } from '../../Tool.js'
import { lazySchema } from '../../utils/lazySchema.js'
import { toErrorResult } from '../../utils/toolResult.js'
import { ARXIV_SEARCH_TOOL_NAME, DESCRIPTION } from './prompt.js'

const inputSchema = lazySchema(() =>
  z.strictObject({
    query: z.string().min(2).describe('arXiv query string. Supports AND/OR/ANDNOT, e.g. "retrieval augmented generation AND low-resource"'),
    maxResults: z.number().int().min(1).max(50).optional()
      .describe('Maximum number of papers to return. Defaults to 10. Prefer 10-20; larger values waste context.'),
  }),
)
type InputSchema = ReturnType<typeof inputSchema>

const outputSchema = lazySchema(() =>
  z.object({
    papers: z.array(z.object({
      arxivId: z.string(),
      title: z.string(),
      authors: z.array(z.string()),
      year: z.number(),
      abstract: z.string(),
      url: z.string(),
    })),
    totalReturned: z.number(),
    cached: z.boolean(),
  }),
)
type OutputSchema = ReturnType<typeof outputSchema>
export type Output = z.infer<OutputSchema>

export const ArxivSearchTool = buildTool({
  name: ARXIV_SEARCH_TOOL_NAME,
  async prompt() { return DESCRIPTION },
  get inputSchema(): InputSchema { return inputSchema() },
  get outputSchema(): OutputSchema { return outputSchema() },

  isConcurrencySafe() { return true },   // 只读 HTTP，可并行
  isReadOnly() { return true },          // 可走缓存

  async validateInput({ maxResults }): Promise<ValidationResult> {
    if (maxResults !== undefined && maxResults <= 0) {
      return { result: false, message: 'maxResults must be >= 1', errorCode: 1 }
    }
    return { result: true }
  },

  async call(input, { abortController, trace }) {
    try {
      const papers = await searchArxiv(input.query, input.maxResults ?? 10, abortController.signal)
      trace({ event: 'tool_ok', tool: ARXIV_SEARCH_TOOL_NAME, n: papers.length })
      return { data: { papers, totalReturned: papers.length, cached: false } }
    } catch (e: unknown) {
      // 工具层永不 throw：转成可判定的错误结果，让模型有机会自我修正
      return toErrorResult(ARXIV_SEARCH_TOOL_NAME, e, {
        code: 'ARXIV_UNAVAILABLE',
        hint: 'If the network is unavailable, retry once; if it still fails, tell the user the search source is down instead of inventing papers.',
      })
    }
  },

  mapToolResultToToolResultBlockParam(output, toolUseID) {
    const body = output.papers
      .map(p => `${p.arxivId} | ${p.year} | ${p.title}\n  ${p.abstract.slice(0, 600)}`)
      .join('\n\n')
    return {
      tool_use_id: toolUseID,
      type: 'tool_result',
      content: output.papers.length === 0
        ? 'No papers found. Try broader keywords.'
        : body,
    }
  },
} satisfies ToolDef<InputSchema, Output>)
```

**规则 5.3**：`prompt()` 必须写"何时用 / 何时不用"。源码 `Tool.description` 的注释说明了理由（`src/Tool.ts:372-378` 的 `searchHint` 要求"3–10 个词、不含工具名已有的术语"），本质是**让模型能区分工具**，而不是描述功能。
**规则 5.4**：`call` 内部 `try/catch` 兜住一切，返回错误结果而非抛出。
**规则 5.5**：错误结果必须带 `hint`，告诉模型下一步怎么做。这是"不炸主循环"与"能自愈"的分界线。
**规则 5.6**：`mapToolResultToToolResultBlockParam` 里做**面向 token 的裁剪**（上例 `slice(0, 600)`）与**空结果的可行动提示**（"Try broader keywords"）。源码在 `GlobTool` 里对空结果返回 `'No files found'`、对截断结果追加建议（`GlobTool.ts:177-196`），同一思路。

出处：`src/Tool.ts:362-500,707-793`、`src/tools/GlobTool/GlobTool.ts` 全文。

## 6. 函数与模块 API 设计

**规则 6.1**：参数超过 3 个时用 options 对象，参数名自带语义。

```ts
// src/Tool.ts:386
description(input, options: { isNonInteractiveSession: boolean; toolPermissionContext: ToolPermissionContext; tools: Tools }): Promise<string>
```

**规则 6.2**：可选参数用 `?`，且在 JSDoc 里写清默认值行为；不用 `null` 表示"未提供"。
**规则 6.3**：函数返回 Promise 还是同步值必须稳定——不要出现"有时同步有时异步"的返回。
**规则 6.4**：模块级导出的函数控制在 5 个以内；超出的应拆文件。`src/utils/` 下 329 个模块是这条规则的直接结果。
**规则 6.5**：不使用 `class` 承载业务逻辑。源码只在错误类型上用了 `class`（`ClaudeError`、`AbortError`、`ConfigParseError`，`src/utils/errors.ts`），其余全用函数 + 类型。

## 7. 异步、并发与取消

**规则 7.1**：`AbortSignal` 必须从入口一路传到最底层的 I/O。源码里 `call(input, { abortController })` 是工具签名的第一个解构项，所有下游函数（`glob(..., abortController.signal)`，`GlobTool.ts:158-164`）都接收它。

**规则 7.2**：工具的并发安全性必须显式声明，默认 `false`。

```ts
isConcurrencySafe() { return true }   // 只读外部查询
```

主循环按此分桶：`isConcurrencySafe() === true` 的一起 `Promise.all`，其余串行。

**规则 7.3**：并发安全 ≠ 可缓存。缓存看 `isReadOnly()`。两者都要显式声明。

**规则 7.4**：每个工具必须有超时。源码把上限放 `constants/toolLimits.ts`，不要在工具里写魔法数字。

**规则 7.5**：并行执行结果必须**按原始顺序**回填。这不是风格问题——Anthropic API 要求 `tool_result` 与 `tool_use` 一一对应且顺序一致，顺序错会直接 400。

## 8. 错误处理

**规则 8.1**：错误类型用 `class XxxError extends Error`，且在构造函数里设 `this.name = this.constructor.name`：

```ts
// src/utils/errors.ts:5-10
export class ClaudeError extends Error {
  constructor(message: string) {
    super(message)
    this.name = this.constructor.name
  }
}
```

理由：压缩构建会破坏 `constructor.name`，源码 `isAbortError` 的注释专门记录了这一点（`errors.ts:18-27`），所以判断用 `instanceof` 而非字符串匹配。

**规则 8.2**：每类错误配一个 `isXxx(e: unknown): boolean` 守卫，集中放在 `utils/errors.ts`。
**规则 8.3**：错误码用常量，不用散落的数字。源码 `ValidationResult.errorCode: number` 在工具内自增（1、2），跨工具的错误码放 `constants/errorIds.ts`。
**规则 8.4**：面向模型/用户的错误文案单独定义常量（`PROMPT_TOO_LONG_ERROR_MESSAGE`），不在抛出点拼字符串。
**规则 8.5**：**工具层不抛，循环层不 catch。** 边界只有一个：注册表的 `executeAll`。源码把这条边界放在 `query.ts` 的工具执行段，本项目收窄到 `tools.ts` 的 `executeAll`。
**规则 8.6**：禁止空 `catch {}`。至少要 `logError(e)`。

## 9. 状态管理（主循环）

源码 `queryLoop` 的结构值得完整照搬，它解决了"多轮循环 + 中途多分支 continue"的状态一致性难题：

```ts
// src/query.ts:252-277（结构重述）
// 1) 不可变参数一次性解构，之后永不重新赋值
const { systemPrompt, userContext, canUseTool, maxTurns } = params

// 2) 可变的跨迭代状态收进单个对象
let state: State = { messages: params.messages, toolUseContext, turnCount: 1, ... }

while (true) {
  // 3) 每轮开头解构，循环体内用裸名读取
  const { messages, toolUseContext, turnCount } = state
  // ...
  // 4) continue 之前整体替换，而不是逐字段赋值
  state = { ...state, transition: 'next_turn' }
}
```

**规则 9.1**：函数的入参（`params`）在整个生命周期内不变；所有可变状态收进一个 `state` 对象。
**规则 9.2**：多分支控制流里，用 `state = { ...state, ... }` 整体推进，禁止在 5 个地方分别改 5 个字段——源码注释明确写了这样做的原因（"Continue sites write `state = { ... }` instead of 9 separate assignments"）。
**规则 9.3**：`while (true)` 允许，但循环体内必须存在至少一条退出路径（`maxTurns`、预算、`return`），且要在紧邻处注释说明。
**规则 9.4**：依赖注入用于测试。源码 `const deps = params.deps ?? productionDeps()`（`query.ts:259`）——单点替换 LLM 与工具执行器，测试无需 mock 全局。

## 10. 流式与生成器

**规则 10.1**：主循环用 `async function*` 返回事件流，而不是回调集合。

```ts
// src/query.ts:241-249
async function* queryLoop(params, consumedCommandUuids): AsyncGenerator<
  StreamEvent | Message | TombstoneMessage,  // yield 的类型
  Terminal                                    // return 的类型
> { ... }
```

理由：调用方按需消费（TUI 实时渲染、脚本收集结果、测试逐条断言），不消费不执行。
**规则 10.2**：生成器内部 `yield` 的事件类型必须是 discriminated union，每种事件带 `type` 字面量。
**规则 10.3**：清理逻辑用 `using`（显式资源管理）或 `try/finally`，保证生成器被提前 `return`/`throw` 时也执行。源码用 `using pendingMemoryPrefetch = startRelevantMemoryPrefetch(...)`（`query.ts:293`），注释写明"disposes on all generator exit paths"。

## 11. 注释与文档

源码的注释密度高，但**几乎没有一句在解释"这行代码做了什么"**。全部是 why。

**规则 11.1**：JSDoc 用第三人称陈述句，首词是动词。

| 写法 | 判定 |
|---|---|
| `/** Returns information about whether this tool use is a search operation. */` | 正确（`Tool.ts:418`） |
| `/** Whether auto-memory features are enabled. */` | 正确（`paths.ts`） |
| `/** 获取用户信息 */` | 错误（what，且第一人称） |
| `/** 这里做了判空，防止报错 */` | 错误（叙述实现） |

**规则 11.2**：注释只记录三类信息——**隐藏约束、不变量、绕过某个问题的原因**。源码范例：

```ts
// src/Tool.ts:41
// Import permission types from centralized location to break import cycles

// src/memdir.ts:28
// ~125 chars/line at 200 lines. At p97 today; catches long-line indexes that
// slip past the line cap (p100 observed: 197KB under 200 lines).

// src/tools.ts:61
// Lazy require to break circular dependency: tools.ts -> TeamCreateTool -> ... -> tools.ts
```

这三条全部在讲"为什么不能按直觉写"。
**规则 11.3**：注释里引用具体文件/符号，方便回源：`(see createSubagentContext)`、`(GlobTool.ts:177)`。
**规则 11.4**：假设/边界用 `SECURITY:` 之类的前缀标出。源码 `GlobTool.ts:100` 有 `// SECURITY: Skip filesystem operations for UNC paths to prevent NTLM credential leaks.`
**规则 11.5**：不写"修改记录"式注释（`// 2026-10-26 张三改成异步`）。历史归 git。
**规则 11.6**：删除代码时连注释一起删，不留 `// 原实现：...` 的尸体。

## 12. 日志与可观测性

**规则 12.1**：区分三个级别，函数名固定：

| 用途 | 源码函数 | 本项目 |
|---|---|---|
| 业务事件（结构化） | `logEvent(name, metadata)` | `traceEvent(event)` → JSONL |
| 调试日志（默认关闭） | `logForDebugging(msg)` | `logDebug(msg)` |

**规则 12.3**：任何上报字段都要能加 `SafeForTelemetry` 标注；文件路径、代码片段、论文正文一律不上报。
**规则 12.4**：日志必须可解析。一行一条 JSON，不打印多行美化对象——源码 `src/cli/ndjsonSafeStringify.ts` 专门处理这个问题。
**规则 12.5**：工具执行的成对日志（`tool_start` / `tool_ok` / `tool_error`）必须带同一个 `toolUseId`，否则并行时无法还原因果。

## 13. 特性开关与死代码消除

源码用 `feature('XXX')` + 条件 `require`，让未启用的分支**在构建期被完全剔除**：

```ts
// src/tools.ts:25-28
const SleepTool =
  feature('PROACTIVE') || feature('KAIROS')
    ? require('./tools/SleepTool/SleepTool.js').SleepTool
    : null
```

**规则 13.1**：**本项目不采用这套机制**。它是为"一套代码发多个内部版本"设计的，与"4 天做一个 demo"无关，照抄只会让代码更难读。
**规则 13.2**：本项目只允许一种开关：**环境变量控制的功能开关**，且必须走 `isEnvTruthy()` 统一解析：

```ts
// src/utils/envUtils.ts:32-37
export function isEnvTruthy(envVar: string | boolean | undefined): boolean {
  if (!envVar) return false
  if (typeof envVar === 'boolean') return envVar
  return ['1', 'true', 'yes', 'on'].includes(envVar.toLowerCase().trim())
}
```

**规则 13.3**：禁止直接 `process.env.X === 'true'`。源码把这定为 lint 规则（`custom-rules/no-process-env-top-level`，见 `src/tools.ts:15` 的 eslint-disable），本项目可放宽到"只在 `config.ts` 内允许"。

出处：`src/tools.ts:14-53`、`src/utils/envUtils.ts`。

## 14. 配置与环境变量

**规则 14.1**：所有 `process.env` 读取集中在一个文件。源码是 `utils/envUtils.ts` + 各模块的 `isXxxEnabled()` 判定函数。
**规则 14.2**：配置判定函数命名为 `isXxxEnabled()`，返回 boolean，内部完成"env → settings → 默认值"的优先级链。源码 `isAutoMemoryEnabled()` 的 JSDoc 用 1-2-3-4-5 五级列清了优先级——**优先级链必须写进注释**，否则没人能预测运行时行为。

## 17. 反模式清单（Do Not）

| 反模式 | 为什么禁止 | 源码对照做法 |
|---|---|---|
| 手写 JSON Schema | 与 Zod 双写必然漂移 | `lazySchema` + `z.infer` |
| 工具里 `throw new Error` | 会让整轮中断，模型失去自愈机会 | 返回错误结果 + `hint` |
| `catch {}` 静默吞错 | demo 现场最难查的一类 bug | `logError(e)` 后返回结构化错误 |
| `as any` 打通类型 | 类型系统失效后，重构等于重新开发 | 收窄守卫 / 泛型 |
| 在工具里读 `process.env` | 无法测试、无法统一默认值 | `config.ts` + `isXxxEnabled()` |
| 用一个巨型 `utils.ts` | 最终变成 3000 行无人敢改 | 一函数一文件（`utils/` 329 个模块） |
| 工具名写成字符串字面量 | 改名后注册表/权限/prompt 三处失配 | `XXX_TOOL_NAME` 常量 |
| 循环里逐字段改状态 | 中途 continue 后状态不可推理 | `state = { ...state }` |
| 日志打完整论文正文 | token 与隐私双输 | 只打 `inputHash` / 长度 / ID |
| 复制源码的 40 个 Tool 方法 | 90% 服务于 TUI，成本全在维护 | 只留 9 个行为性成员 |

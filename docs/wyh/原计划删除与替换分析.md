## 0. 一句话

**这次要讨论的，是「agent 主循环由谁执行」这一个问题，并非「要不要 agent」。**

- 如果答案是「平台执行」→ 删 6 个文件，项目定位为**沉淀与治理层**
- 如果答案是「我们自己执行」→ 6 个文件全留，3 天内做不完 A/B，必须砍掉其中一个模块
- **没有第三条路。** 两种做法并行 = 两套上下文管理都半成品，这是 4 天项目最典型的死法

---

## 1. 触发讨论的三个事实（都是实测，不是推测）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 平台**有**完整 agent 运行时 | `agent/initiate`、`thread/{id}/agent/start`、`agent-run/{id}/stream`、`/audit`、`/checkpoint`、`/resume`、`/handoff`、`tool-policy`、`tool-approvals` |
| 2 | 平台**没有**知识库原语 | 全站 `knowledge-base` 仅 4 个端点，且 `connections` 官方描述写明存的是 **RAGFlow 连接**（要传 endpoint + key）。`dataset` / `chunk` / `rag` 关键词全站零命中 |
| 3 | 平台**没有**工具定义原语 | `/api/mcp/*` 5 个端点全部只读，无"注册 MCP"；工具只能在**建 agent 时**通过 `configured_mcps` / `custom_mcps` / `tool_profile` 绑定 |

这三条决定了删除边界：**有原语的才交，没原语的不能交。**

## 2. 判据（按顺序问，三个问题定生死）

| 序 | 问题 | 是 → | 否 → |
|---|---|---|---|
| ① | 这个能力是不是平台的**一等公民**（有专有端点、有官方语义） | 可全权交 | 只交"生成"，其余自建 |
| ② | 是否需要**平台外的状态**（文件树、页码锚点、git、版本锁） | 必须留本地 | 可交 |
| ③ | 失败是否**静默**（跑通了但结果错） | 必须本地校验 + 人工确认 | 可交 |

拿这三条过一遍 6 个文件，结论才会稳。比如 `parse.ts`：PDF 解析是平台一等公民（①是），但页码锚点是平台外状态（②否），所以**解析可交、锚点必须自建**——这正是下面 `parse.ts` 被删但 `verify-anchors.mjs` 新增的原因。

### 7.1 若表决结果是「保留自研 loop」，为什么被砍的是 B

**先说清一件事：保留自研 loop ≠ 不做 SciencePal。** 提交物②要求交一个可访问的 SciencePal Agent 链接，核心环节要实质性使用它。**这条门槛不因自研而消失。** 所以自研 loop 是**纯增量**，不是替代方案 —— 你们会同时维护两条链路。这决定了削减压力的来源。

依据三条，按硬度排序：

| # | 依据 | 出处 |
|---|---|---|
| 1 | **B 已经是降级第一顺位**，不是我现编的 | `docs/SDD.md` §13.3 原文：「D2 17:00 A 闭环跑通 \| 未通过则 **砍 B 至 1 个工具**，C 改手工编写」 |
| 2 | **B 在依赖链最末端**：`PaperDoc` → `MethodSpec` → 工具代码 → `registry` 注册 → `smoke` 执行。五个环节的前四个都依赖别人 | `STRUCTURE.md` §9 + `toolsynth/README.md` |
| 3 | **B 是唯一有静默错误风险的模块**：生成的分析代码可能"跑通了但结果错"，现场最难自证 | `SRS.md` / 风险登记 R-1：可行性「中」，是三模块里唯一有真实失败风险的 |

补充两条次要依据：

- **B 的 demo 效果最弱**：一段生成的 JS 代码投在屏幕上，评委看不出价值；而 A 的知识页有可视化、C 的技能有准确率差值。
- **B 的执行已交给平台 sandbox**，本地只剩生成器 —— 它原本最重的部分已经不在我们手上，所以「砍它」损失的绝对价值最小。

#### 增量成本量化（保留自研 loop 要多付多少）

| 项 | 估行数 | 估工时 | 说明 |
|---|---|---|---|
| `llm/{deepseek,stream,retry}.ts` | ~350 | **6h** | AGENTS.md ④ 列的 5 处协议差异，每处都要对真 API 实测 |
| `paper/parse.ts`（pdfjs + 页码映射） | ~250 | **6h** | 页码映射是本轮实测确认的坑（见附录 A） |

#### 但「必须砍 B」这个说法不严谨 —— 触发条件在这里

如果增量小于 12h，B 可以不砍，改砍别的：

| 若增量实际是 | 建议削减对象 | 代价 |

| ≥ 12h | **B 降为 1 个工具**（沿用 SDD 既定方案） | 少一个模块的完整度，保住 A/C/Web |

## 附录 A：精读探针实测结论（2026-10-28 20:15，真实 run）

用 ReAct（arXiv 2210.03629，ICLR 2023）跑了一次精读模式，这条结果**直接改变了 A 模块的设计**：

| 指标 | 结果 |
|---|---|
| 论断条数 | 20 条（method / result / limitation 三类齐全） |
| quote 能在原文定位到 | **20 / 20（100%）** ← 说明引用真实，没有编造 |
| 自报页码与 PDF 物理页码一致 | **0 / 20（0%）** |
| 偏移分布 | +1 有 12 条，+2 有 7 条，其他 1 条 |
| 耗时 / 消耗 | 151.9s / **421,904 tokens**（400k 预算被耗尽，状态 `asked`） |

### 结论：**不要问模型"在第几页"，要让它给 quote，页码由本地反查**

原设计假设"平台会给页码锚点，`locator` 白捡"。实测推翻了这个假设：

- 好消息：**quote 100% 可定位**，说明它读的是真原文，抽取本身可信
- 坏消息：**页码 100% 错**，偏移还在 +1/+2 之间跳变，无法用固定补偿修正

因此 A 模块的正确架构是：

```
平台精读 → 返回 {claim, quote, section}     ← 不要 page
    ↓
本地 pdftotext 按页切分
    ↓
verify-anchors.mjs 用 quote 反查页码 → 覆盖模型自报值
    ↓
AtomicNote { locator: "p.6 §3.3" }         ← 页码 100% 可复现
```

新增的 `scripts/verify-anchors.mjs` 就是这个反查器，同时兼任 A 模块的质量门（`pageAccuracy` / `locateRate` 两个指标）。**这比原计划更可靠**：原计划信任模型自报页码，本项目现在用确定性工具核验。

### 成本警示

单篇 33 页论文消耗 **42 万 token**（含平台 2.4 万固定开销）。若演示要跑多篇，必须先算清额度；`token_budget` 建议 ≥ 400k，且脚本必须正确处理 `asked` 状态（它不是失败，是"暂停等你决定"）。

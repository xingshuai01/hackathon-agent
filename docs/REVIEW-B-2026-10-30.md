## 一、整体评价:值得表扬的五个设计

### 1. `extract.ts` 复用了 A 模块的血泪教训

不信任模型自报页码(模块 A 实测 20 条错 20 条),对 LLM 给的 `evidenceQuote`
做**逐字回指校验**:声称页找不到 → 全文反查 → 改判真实页;全文找不到 → 丢弃并记录。
这是「不静默丢弃」(AC-B2.5)的正确落法。

### 2. `generate.ts` 永不 throw

所有「生成不了」的情况都变成 `result.skipped` / `draft.reason`,没有一条
会让整个流水线崩掉。与铁律 8 完全一致。

### 3. `render.ts` 把 DEC-019 落得干净

LLM 只抽结构(`MethodSpec`),代码由模板填出,实现来自 `impls.ts` 的确定性 L1 目录。
无实现的方法降级为「参数模板 + 人工填写」—— 绝不静默丢弃,也绝不产生任意代码。

### 4. smoke 与 CI 同一条路径

`runSmokeTest` 用 `node --test`(与 `npm test` 一致),不是自造一套判断。
「每个生成工具必须有 .test.ts」是硬约定,缺文件按 smoke 失败计。

### 5. 数据铁律 #2 双保险

`evidencePage` 在 `types.validateSpec`(结构校验)和 `extract.locateQuotePage`(回指校验)
两处都卡,不只靠自觉。

## 二、发现的缺陷与修复

### 🔴 P1-1 · 跨字段校验缺失 → 静默错误

**现象**(实测):

```
success_rate(11, 10) → 接受 → "成功率 110.0%(11/10)"
```

**根因**:zod 的字段级校验(`.min/.int`)管不了「successes <= total」这类
**跨字段**语义约束。生成的工具没有用 `Tool` 契约里的 `validateInput` 钩子。

**影响面**:3 个工具 —— `success_rate`、`webshop_score`、`should_backoff_to_react`。
这正是风险登记册 R-1 说的「跑通了但结果错」,现场最难自证。

**修复**:

1. `impls.ts` 的 `L1Impl` 增加可选 `validateSource`(跨字段校验源码,返回 `{ok}` 或 `{ok:false,message}`)
2. 三个实现各补一条约束(`successes<=total` / `matchedCount<=requiredCount` / `majorityCount<=total`)
3. `render.ts` 渲染成工具的 `validateInput`(call 之前执行,零 I/O)
4. 重新生成工具 + 新增 6 个回归测试

**验证**:

| 输入 | 修复前 | 修复后 |
|---|---|---|
| `success_rate(11,10)` | 接受 110% | ✅ 拒绝「successes 不能大于 total」 |
| `webshop_score(matched>required)` | 接受 | ✅ 拒绝 |
| `should_backoff(majorityCount>total)` | 接受 | ✅ 拒绝 |
| 合法输入 | — | ✅ 不受影响 |

### 🟠 P2-1 · smoke 在受限环境无法运行

**现象**:本机沙箱里 `spawnSync(stdio:'pipe')` 返回 EPERM → 4 个测试失败
(`npm test` 变成 357/362)。同学机器与 CI 上正常。

**根因**:`smoke.ts` 用管道捕获子进程输出,而沙箱禁止「带管道 stdio 的 spawn」。

**修复**:`runSmokeTest` 检测到 EPERM 时退化为 `stdio:'ignore'` ——
拿不到输出文本,但**退出码仍然可靠**,smoke 照常判 pass/fail。

**验证**:修复后 `tools doctor` 恢复 5 active / 1 draft(通过率 83%)。

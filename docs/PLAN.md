# 四天开发计划

> 时间:4 天 · 团队:偏工程 · 唯一硬目标:**D4 能现场演示一条端到端跑通的链路**
> 参考:《黑客松选题与Claude_Code技术框架》中的 Claude Code 架构分析与三个候选选题

---

## 0. 选题(待锁定,D1 上午必须定)

| 候选 | 核心挑战 | 工作量(原文估算) | 一句话判断 |
|---|---|---|---|
| **A. PaperAgent** | 多 agent 协作 + 长文档 | 核心 2-3 天 / 完整 4-5 天 | 覆盖 Agent 核心机制最全,**若只做核心范围,4 天够** |
| **B. LabNotebook Agent** | 后台任务 + 持久化记忆 | 核心 2 天 / 完整 3-4 天 | 时间最稳,但 demo 观感偏"后台",现场不好看 |
| **C. LiteratureSurvey Agent** | 工作流编排 + 结构化输出 | 核心 3 天 / 完整 5 天 | demo 最直观,但 5 天估算是 4 天的 1.25 倍,偏紧 |

### 决策规则

1. **第一约束是"4 天内端到端能跑"**,不是功能最全。
2. 选 A 就必须**只做核心范围**:砍掉 PDF 表格/图表精读、砍掉完整复现代码仓库、砍掉多语言输出。
3. 锁定后立刻:把本节标题改为最终选题 → 建对应 Milestone → 把 D2/D3 的任务拆成 Issue。

## 1. 里程碑

| 里程碑 | 目标 | 验收标准(可演示 = 通过) |
|---|---|---|
| **M1 · 骨架** (D1) | 框架跑通 | 输入一个 prompt,主循环能完成「调 LLM → 解析 tool_use → 执行工具 → 回填 → 再生成」至少 1 轮,终端能看到过程 |
| **M2 · 核心能力** (D2) | 工具可用 | ≥3 个真实工具(至少 1 个访问外部数据源);1 个子 Agent 能被主 Agent 调度并返回结果 |
| **M3 · 端到端** (D3) | 链路贯通 | 一条命令从输入到产出最终交付物(报告/代码/综述),中间无需人工干预 |
| **M4 · 交付** (D4) | 可演示 | 一键 demo 脚本 + 3 分钟录屏 + README 讲清"借鉴了 Claude Code 的哪个机制" |

## 2. 每日任务结构

> 具体任务以 GitHub Issue 为准,这里只给骨架。每个 Issue 必须写清验收标准。

### D1 — 骨架
- [ ] 选题锁定 + 建 Milestone
- [ ] 项目脚手架(语言/依赖/目录/一行启动命令)
- [ ] `Tool` 接口抽象(JSON Schema 描述参数 + 统一执行入口)
- [ ] LLM 主循环(streaming + tool_use 解析 + 结果回填)
- [ ] 最小 CLI/TUI 能看过程

### D2 — 核心能力
- [ ] 3+ 真实工具
- [ ] 子 Agent 机制(独立上下文 + 独立工具白名单)
- [ ] 最小记忆(文件式持久化,记录"已处理过的内容")
- [ ] 错误处理:工具失败不炸主循环

### D3 — 端到端
- [ ] 串起完整 pipeline
- [ ] 可复现的 demo 输入(固定样例,别用现场随机数据)
- [ ] 上下文控制(长输入的分段/摘要策略)
- [ ] **代码冻结线:当天结束前 main 必须能跑通完整链路**

### D4 — 交付
- [ ] 一键 demo 脚本
- [ ] 3 分钟录屏(先脚本化,别现场手打)
- [ ] README / 幻灯片:架构图 + "借鉴了 Claude Code 的什么"
- [ ] 仓库清理(密钥、无关文件、私密信息)

## 3. 风险与预案

| 风险 | 触发信号 | 预案 |
|---|---|---|
| 选题范围过大 | D2 结束还没跑通 M2 | 立刻砍掉子 Agent 协作,退化为单 agent 多工具 |
| LLM API 不稳 / 额度不足 | 频繁 429 / 超时 | 提前测通 2 个 provider;关键路径加缓存与重试 |
| 长文档上下文炸 | 输入即超限 | D3 前必须落地分段摘要,不要等现场 |
| 现场网络问题 | — | demo 用预跑产物兜底,录屏作为备份 |
| 并行开发冲突 | 频繁 merge 冲突 | 文件级分工,`main` 每日可跑,冲突当天解掉 |
